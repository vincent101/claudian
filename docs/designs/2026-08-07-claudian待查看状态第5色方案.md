# Claudian tab badge 第 5 色"运行完待查看"方案

## 背景与问题

Claudian 2.0.11（本地 bundle，已打 attention patch，见 [[2026-08-06-claudian标题栏等待回答状态颜色方案]]）现有 4 个 badge 状态：蓝(active) / 红(attention=等待回答) / 绿(streaming) / 灰(idle)。需新增第 5 色，语义为"**运行完了，但用户还没看过这个 tab，需要检查**"——即上游 2.1.x 的 `TabAttentionKind = 'review'`。

本文档是上一份 attention 设计的演进：上一份接通"等待输入"（action-required），本份接通"跑完待看"（review），并给它独立颜色（上游 review 与 action-required 同色，本方案超出上游之处仅在于分色）。

**可行性结论：可行。** 依据：上游 2.1.2 有完整 review 状态机可对照（本地已浅克隆至 `/tmp/claudian-upstream`，commit `f9285b8`，2026-08-07）；2.0.11 bundle 未压缩、流结束与 tab 激活均有唯一收敛点可挂；复用现有回调链，无需新增callback 接线。

## 上游 review 状态机（2.1.2 精读结论）

### 置 review（全部条件同时满足）

1. **结局有资格**：turn 结局为 `completed`，或 `error && accepted`（已真正发给 provider 后出错）；`cancelled`（用户中断）/ `invalidated`（会话切换/关闭）/ `missing-session` / 发送前失败均**不置**（`InputController.ts:511-512`、`517-522`、`567-571`）。
2. **最终闸门**：`!didCancelThisTurn && !planApprovalInvalidated && streamGeneration 未变`（`InputController.ts:721-724`）。
3. **续跑延迟（defer）**：若有排队消息/plan 自动发送接续，review 报告被 deferred 到整条续跑链结束才结算（`InputController.ts:688-689`、`727-729`、`922-938`）。
4. **tab 全程在后台**：capture 时 `activeTabId !== tab.id`，且 report 时 `tabActivationRevisions` 未变——即结算窗口内用户没有激活过该 tab（`TabManager.ts:213-226`）。capture 发生在流结束后（非流开始时）。
5. 与 action-required 共存：`markReviewRequired()` 在 action-required pending 时把 review 暂存为 `pendingReviewSince`，待 `endActionRequired` 清空后降级回 review（`ChatState.ts:319-349`）。
6. 异步 subagent 完成、后台 turn 完成也走同一 capture→report（`Tab.ts:894`、`933`，2.1.x 特有路径，2.0.11 无此概念）。

### 清除 review

1. **tab 激活**：`switchToTab` 内 `activateTab(tab); tab.state.acknowledgeReview();`（`TabManager.ts:308-309`）——激活即视为"看过"，只清 review、不清 action-required。
2. **发新消息**：`sendMessage` 入口 `state.acknowledgeReview()`（`InputController.ts:365`）。
3. **会话重置**：`resetForNewConversation` → `clearAttention()`（`ChatState.ts:484`）。

### 渲染

上游 review **没有独立颜色**：`needsAttention` getter = `attention !== null`（两种 kind 都算），badge 优先级仍是 `active > attention > streaming > idle`（`TabBar.ts:74-83`），attention 色 `--text-error`（`tabs.css:93`）。

## 2.0.11 bundle 锚点核实（当前文件，含 attention patch）

| 行号 | 代码 | 路径 |

### 中断判别

`cancelRequested = true`：76903（createNew force）、80720（`cancelStreaming`，来自 Escape 89975-89979 / 停止按钮）、90160（ExitPlanMode approve-new-session）。清除点：80069（流开始）、**80206（在 80205 setter 之后一行）**、85542。因此在 80205 setter 同步触发的回调里读 `tab.state.cancelRequested`，中断结束时仍为 `true`、正常/报错结束为 `false`——**可在 TabManager 闭包内零接线区分中断**。Escape/停止按钮只会发生在活跃 tab（keydown 绑在 tab 自己的 inputEl 上），与 active 守卫形成双保险。

### tab 激活落点

所有激活汇聚于 `switchToTab`（90443）：badge 点击 90279 → `onTabClick` 91233 → `handleTabClick` 91312-91315 → `switchToTab`；恢复 90433、openConversation 90584 同。`activateTab(tab)` 全文仅 90462 一处调用。90475 触发 `onTabSwitched` → `updateTabBar()`（91166）——清除 review 挂在此处自带重绘。

### 与 attention 的时序关系（代码依据，非猜测）

- **路径 1-3（工具授权/AskUserQuestion/ExitPlanMode）**：回调从 `agentService.query` 迭代内部发起（setupServiceCallbacks 90112+），此时 for-await 循环（80169）停泊、**isStreaming 仍为 true**（80205 在 finally、循环结束后才执行）。故 attention(路径1-3) 期间 streaming 必为 true，review 不可能在此时被置（流未结束）。
- **路径 4（plan 完成审批）**：80205 先置 isStreaming=false，80246 才 `beginAttention()`。**此刻 review 与 attention 可同时成立**（流刚结束 + 审批未答）。本方案两标志是独立 boolean，天然兼容：优先级 attention > review 保证审批期间显示红色；用户答完 attention=false、review 仍在 → 转黄，语义正确（"答完了，跑完了，去看看"）。
- 上游对应机制（pendingReviewSince 暂存降级）在本方案由独立 boolean 天然覆盖，无需移植。

## 方案设计

### 设计决策（对照上游逐项取舍）

| 决策点 | 上游做法 | 本方案（务实路径） |
|---|---|---|
| 置位条件 | 结局白名单 + defer + revision 守卫 | TabManager 闭包单钩子：`!isStreaming && tab.id !== this.activeTabId && !tab.state.cancelRequested` |
| 中断 | 不置 | 不置（cancelRequested 同步读，与上游一致） |
| 报错结束 | 置（error&&accepted） | 置（无法区分 accepted，初始化失败也会置——见风险节，建议保留） |
| 续跑链 | defer 到链尾 | 不 defer：每 turn 结束都置，streaming 优先级高于 review 使续跑期间显示绿色，链尾自然落黄 |
| "看过"定义 | tab 激活即清除 | 同上游（switchToTab 清除）。发消息清除不移植——发消息必经激活，冗余 |
| 聚焦 tab 跑完 | 不置（shouldReport） | 不置（activeTabId 守卫） |
| 颜色 | 与 attention 同色 | **独立第 5 色**（本方案超出上游的唯一点） |

**优先级：active > attention > streaming > review > idle。** 依据：续跑链中 review 与 streaming 同时成立时须显绿（运行中优先于"跑完"）；plan 审批窗口 review 与 attention 同时成立时须显红（待操作优先于待查看）。

## 风险与权衡

**已核实的安全点**
- 取消/异常不会卡黄：review 只在"看过"（激活）时清除，无计数器、无配对约束，不存在泄漏型卡死；最坏情况是黄标残留到下次点击该 tab，无害自愈。
- 中断不误置：cancelRequested 同步可读（80206 在 80205 之后一行才清零）。
- 续跑链：review 在链中每 turn 结束都被置，但 streaming 优先级更高显示绿色；链尾落黄。视觉正确。
- 状态为 runtime-only：Obsidian 重载后 review 清零（与上游一致，上游注释即 "Runtime-only Attention State"）。

**与上游的已知差异（务实取舍，供确认）**
1. **排队续跑瞬间可能闪黄一帧**：turn1 结束（置黄、rAF 重绘）→ `conversationController.save` await → turn2 开始（转绿），中间有约一次帧绘制的窗口。上游用 defer 机制消除，本方案不移植。纯视觉、自纠正。
2. **中途瞄一眼再切走**：上游的 activationRevision 守卫会抑制"链中看过一眼"后的再置位；本方案在链尾仍会置黄。语义可辩护（"最终输出你没看过"），且更简单。
3. **初始化失败（80137）也置黄**：上游对该路径不置新 review。本方案无法区分，且认为"消息没发出去"本身就值得提醒。保留。
4. **view 级可见性不感知**：TabManager 的 activeTabId 是 view 内概念；整个 Claudian 面板被切到后台时，其"活跃 tab"跑完不置黄（上游同样如此）。感知 Obsidian leaf 焦点需接 workspace 事件，不属务实路径。
5. **bundle 改动风险同上一份**：任何语法错误导致整个插件加载失败，`node --check` 是硬门槛；插件更新即覆盖，需与 attention patch 一起重打。

**残留不确定项（诚实说明）**
- `cancelRequested` 同步可读的结论来自行序推断（80205 先于 80206），未实机验证；验收 4 专测此点。
- 未验证 `--color-yellow` 在当前主题下 2px 边框的实际对比度，需实机目视。

## 需用户确认的问题

1. **色值**：推荐 `var(--color-yellow)`；若实机对比度差，改 `var(--color-purple)`。
2. **报错结束算"待检查"**：推荐算（含初始化失败路径，差异 3 已述）。
3. **用户中断不算**：推荐不算（与上游一致，已内置于 Patch 3 的 cancelRequested 条件）。
4. **"看过"= 激活即清除**：推荐此定义（上游同款）；不采纳更严格的"滚动到底/发消息才算"。
5. **接受与上游的两处行为差异**（续跑闪黄一帧、瞄一眼后链尾仍置黄）。

### 阶段 2：Obsidian 内人工验收（完全重启或禁用/启用插件后）

**验收 1：后台跑完 → 黄**。开 ≥2 个 tab；tab 1 发一条普通指令，立即切到 tab 2；等 tab 1 跑完 → badge 绿转**黄**（不是灰）。

**验收 2：看过即消**。切到 tab 1（变蓝，active 优先）→ 切走 → tab 1 应为**灰**（不再是黄）。

**验收 3：聚焦 tab 跑完不置黄**。停在 tab 1 发指令并看着它跑完 → 切到 tab 2 → tab 1 直接是灰。

**验收 4：中断不置黄**。tab 1 发指令，运行中按 Esc 中断（此时 tab 1 是活跃 tab，双重守卫）→ 切走 → tab 1 为灰。另：后台 tab 运行中直接右键关闭该 tab（force 取消路径）→ 不应残留任何异常。

**验收 5：报错置黄**。tab 1 制造一次失败（如断网后发指令），切到 tab 2 等结束 → tab 1 为黄。

**验收 6：与 attention 叠加**。tab 1 用 plan 模式跑到出审批框（Implement/Revise）后切到 tab 2：审批未答期间 tab 1 应为**红**（attention > review）；切回答复后立即切走 → 若 run 已结束应为**黄**。

**验收 7：续跑链**。tab 1 运行中再排队一条消息，切到 tab 2：续跑期间应显**绿**（streaming > review，允许转瞬即逝的一帧黄）；全部跑完 → 黄。
