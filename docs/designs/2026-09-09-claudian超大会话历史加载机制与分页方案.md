# 背景与问题

Claudian 重载 1.53 GB Claude transcript 时没有设计性“最近 N 条”策略，而是整文件读取触发 V8 字符串上限后静默失败；多 session 合并逻辑又把成功加载的较小历史段当成有效结果，造成“数据仍在盘、tab 只显示部分历史”的假性截断。

# 方案设计

## 一、机制定位与判定

### 1. 重载链路

1. 插件启动只从 metadata 恢复会话壳，`messages` 明确初始化为空：`/Users/vincentwang/Documents/NoteVault/tools/claudian/src/main.ts:311-331`。
2. tab 恢复只保存 `tabId + conversationId`，不保存消息：
   - `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/tabs/TabManager.ts:646-664`
   - `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/ClaudianView.ts:612-619`
3. 恢复 active tab 后，`ConversationController.loadActive()` 调 `plugin.getConversationById()`：`/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/controllers/ConversationController.ts:182-229`。
4. `getConversationById()` 调 provider history hydration：`/Users/vincentwang/Documents/NoteVault/tools/claudian/src/main.ts:588-592,691-698`。
5. Claude hydration 顺序读取 `previousProviderSessionIds` 和当前 session，并调用 `loadSDKSessionMessages(...)`：`/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/ClaudeConversationHistoryService.ts:357-405`。
6. `loadSDKSessionMessages()` 先 `readSDKSession()`，再做 branch 过滤、tool result 收集和 UI message 映射：`/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/ClaudeHistoryStore.ts:60-169`。
7. `readSDKSession()` 使用 `fs.readFile(..., 'utf-8')` 整文件解码，再 `split('\n')`，再逐行 `JSON.parse`：`/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/sdkSessionPaths.ts:69-98`。
8. 成功后 `restoreConversation()` 把全部 message 放进 `ChatState`，`MessageRenderer.renderMessages()` 同步遍历创建全部 DOM：
   - `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/controllers/ConversationController.ts:439-487`
   - `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/rendering/MessageRenderer.ts:193-215`

### 2. `truncateAt` 的真实语义

`ClaudeConversationHistoryService.ts:393-397` 中变量名 `truncateAt` 容易误导。它传入的是 `resumeAtMessageId`，只用于 rewind/fork 的 branch checkpoint，不是条数或字节上限：

- `filterActiveBranch(entries, resumeAtMessageId)` 先建立 UUID/parent 图，再在分支场景沿祖先链选择目标 leaf：`/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/sdkBranchFilter.ts:23-270`。
- 无分支且无 checkpoint 时直接返回全部 conversation entries：同文件 `:174-178`。

结论：源码中不存在“最近 N 条”或“超过 X MB 截断”的设计保护。

### 3. 此会话的实际失败方式

已对真实文件做无正文输出的验证：

- 当前 transcript：1,536,935,229 bytes，32,284 行；无坏 JSON 行。
- Node 当前 `buffer.constants.MAX_STRING_LENGTH = 536,870,888`。1.53 GB 文件执行与源码等价的 `fs.promises.readFile(path, 'utf8')`，即使 `--max-old-space-size=4096` 仍直接报 `RangeError: Invalid string length`；256 MB heap 下则 OOM。
- 失败被 `sdkSessionPaths.ts:94-97` 捕获并转换成 `{messages: [], error}`，没有日志、Notice 或 telemetry。
- 该 conversation metadata 同时引用：
  - 当前 session `b769...`：1.53 GB，必失败；
  - previous session `9d5e...`：8.76 MB，3,331 行，可成功。
- `ClaudeConversationHistoryService.ts:408-411` 只有“全部非缺失 session 都失败”才整体 return。这里 previous session 成功，所以当前 session 的错误被忽略，成功片段继续合并；随后 `:430-431` 写入 `conversation.messages` 并标记已 hydrated，本次插件生命周期不再重试。

因此用户看到的并非“当前 1.53 GB 文件读到某个位置后截断”：当前文件是**整段零贡献**；tab 中残留的是其他成功 session 段和/或重载后新增的内存消息。视觉上可表现为“只剩一部分”，但不是稳定的“最近 N 条”。

### 4. 性能放大因素

即使绕过 V8 单字符串硬上限，现链路仍不可扩展：

- `readFile` 字节缓冲 → UTF-8 字符串 → `split` 行字符串 → 全量 JSON 对象，多份峰值驻留。
- 真实文件中约 1.482 GB 来自 user records，但可显示 user/assistant 文本合计仅约 10.9 MB；说明 hydration 把大量 UI 不需要的结构化 payload 一并保留、解析。
- 最大单行约 6.84 MB，不能假设“逐行即小对象”。
- Python 流式 JSON 解析全文件约 4.1 秒、峰值 RSS 约 242 MB；仅流式扫字节约 0.67 秒、峰值 RSS 约 60 MB。Electron 主线程再叠加 JS 对象、branch maps、tool result maps 和 DOM，成本更高。
- target metadata 的 `subagentData` 有 254 项，JSON 序列化约 78.9 MB；插件启动阶段还会额外加载这部分。
- branch filter 算法主体是 O(n)，不是根因；问题是它要求全量 `SDKNativeMessage` 常驻后再建多组 Map/Set/数组。
- UI 无虚拟化，`renderMessages()` 对所有消息建 DOM；Markdown 渲染又逐消息异步启动。reader 修好后，瓶颈会从读取转移到内存和 DOM。

### 5. 判定

这是 **bug / 未受控规模失效**，不是设计性保护：

- git blame 显示整文件读取与全量 hydration 自 2026-04-06 的 multi-provider 重构引入；注释和 provider 文档均表达“加载完整消息集”，没有上限设计。
- `MessageRenderer` 同样明确写着 “Renders all messages”。
- 错误被静默吞掉、多个 session 部分成功后仍标记 hydration 完成，违反完整性语义。

## 二、多方案评估

### 方案 A：提高上限 / 增大 heap

**做法**：提高 Electron/Node heap，继续整文件读取和全量渲染。

**优点**：改动最小。

**缺点**：

- 1.53 GB 已超过 V8 单字符串约 512 MB 的硬上限，单纯提高 heap 无效。
- 即便改为 Buffer 后分段转字符串，仍会保留全量 JSON、tool payload、映射对象和 DOM，只是把崩溃点后移。
- 会话继续增长，不能形成稳定边界。

**结论**：否决；仅可作为诊断手段，不能作为方案。

### 方案 B：流式全量 hydration + 全量 DOM

**做法**：以 readline/chunk reader 替代 `readFile + split`，边读边 parse；branch 仍在内存完成，最终渲染全部消息。

**优点**：

- 消除单字符串硬上限。
- 可复用现有 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/transcript/ClaudeTranscriptTailReader.ts` 的 chunk/partial-line 处理思想。
- 改动范围中等。

**缺点**：

- branch 图、tool result、ChatMessage、78.9 MB subagent metadata 和全量 DOM 仍常驻。
- 初次打开需扫完整 1.5 GB；主线程若不隔离仍会卡 UI。
- 只是把“不能加载”变成“很慢且高内存”。

**结论**：可作为过渡修复，但不足以支撑持续出现的超长会话。

### 方案 C：轻量索引 + 最近页首屏 + 向上分页 + DOM 窗口化（推荐）

**核心原则**：transcript 是事实源；UI history 是按需投影，不再等同于“全部 transcript 常驻内存和 DOM”。Claude resume 的模型上下文仍由 Claude Code 管理，与 UI 分页分离。

#### C1. provider-neutral 分页契约

在 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/core/providers/types.ts` 为 history service 增加可选分页能力，例如：

- `loadInitialHistory(conversation, vaultPath, pageSize)`：返回最近一页、opaque cursor、`hasMore`、诊断状态。
- `loadOlderHistory(cursor, pageSize)`：返回前一页。
- 保留现有 `hydrateConversationHistory()` 作为不支持分页 provider 的兼容路径。

cursor 必须由 provider 持有内部语义，feature 层不得读取 Claude UUID/offset。

#### C2. Claude 两阶段索引

在 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/` 新增流式 index reader；不要直接把 live tail reader 改成历史 reader：两者方向、完成条件和容错语义不同，但复用其“固定字节块 + partial line”底层 primitive。

第一遍仅保留：

- byte offset / line length；
- type、uuid、parentUuid、timestamp；
- branch 判定必要标记（real user、meta、sourceToolUseID、progress）；
- tool use/result 关联 ID；
- 可显示性标记。

随后用索引计算 canonical branch。`sdkBranchFilter.ts` 的规则迁移为“对轻量 index 运行”，不要先构造完整 `SDKNativeMessage[]`。分页时只 seek/read 当前页所需 offset，再映射为 `ChatMessage`。超大单行需设“允许的大行上限 + 明确错误卡片”，不能静默跳过。

索引可先内存构建；32K 行的轻量索引可控。为避免每次重载重扫 1.5 GB，后续将索引缓存到 `.claudian/cache/history/`，key 至少含 absolute path、inode、size、mtime；append-only 增长只增量索引，inode 变化或文件缩短则重建。

#### C3. 首屏与向上分页

修改：

- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/controllers/ConversationController.ts`
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/rendering/MessageRenderer.ts`
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/state/ChatState.ts`

行为：

1. 首次恢复只加载最近 50 个**可见对话 turn**（不是原始 JSONL 行，也不是固定字节数）。
2. 顶部显示“加载更早消息”；接近顶部时每次 prepend 50 turn。
3. prepend 前记录锚点元素及 offset，完成后恢复视觉位置，避免滚动跳动。
4. `ChatState` 增加 history cursor / `hasMore` / loading / error 状态；加载错误必须显示，不得把 incomplete 当 complete。
5. 当前页所需 tool result 必须随页解析；跨页 tool use/result 通过索引关联，不能因分页显示成永久 running。

#### C4. DOM 窗口化

分页解决首屏成本，但用户持续向上翻仍会累积 DOM。设置约 150–250 个已加载 turn 的 DOM 窗口：远离视口的页替换为带精确高度的 spacer；回滚时重建该页。内存中的轻量 `ChatMessage` page 可比 DOM 窗口更大，但也需 LRU 上限。

不建议一开始引入第三方虚拟列表库；现有消息高度高度可变、含 Markdown/tool/subagent 展开态，引入库的适配成本高。先做按页窗口化，比逐项虚拟化简单且可控。

#### C5. 完整性与错误语义

修正 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/ClaudeConversationHistoryService.ts:378-431`：

- 每个 session segment 都返回 `complete | partial | failed` 和错误原因。
- 任一 segment 失败时，会话状态必须标 `partial`，显示缺失 segment；不得静默 `continue` 后标 hydrated。
- `hydratedConversationIds` 只表示初始页已成功建立，不代表“全历史已进内存”。失败允许重试。
- 对当前 1.53 GB 文件，首屏应成功；若索引构建失败，应显示明确错误，而不是空白或其他 segment 冒充完整历史。

#### C6. UI history 与模型 context 解耦

现有 SDK amnesia rebuild 依赖 `conversation.messages` 的“全量”假设。分页后必须把 rebuild 改为 provider history service 的独立流式导出，而不是把 UI 全部翻进内存。正常 resume 仍交给 Claude Code；只有检测到 session ID 异常时才执行完整 context rebuild。

这一步防止为了模型兜底而破坏 UI 的有界内存设计。

### 方案 D：主动分流会话

将长任务在稳定里程碑处分新 session，并用交接摘要/设计记录续接。

**价值**：降低 Claude Code context、transcript、subagent sidecar、UI history 的共同压力；900+ 轮会话已超出适合交互式单会话承载的范围。

**局限**：这是运维策略，不是 correctness 修复。旧会话仍必须可读；不能用“建议新开会话”掩盖 hydration bug。

### M1：启动止血

#### 1. 明确状态机与触发语义

每个恢复 tab 增加仅属 UI 生命周期的 hydration 状态：

`SHELL → SCHEDULED → LOADING → READY | OVERSIZE_BLOCKED | ERROR`

- `SHELL`：只持有 `tabId、conversationId、providerId、title` 等 metadata；不得调用 `getConversationById()`、history hydration、runtime warmup。后台 tab 内容区不挂载；若成为 active，先显示“会话尚未加载”骨架。
- `SCHEDULED`：仅 active tab 在壳已渲染且浏览器完成一帧后进入。调度采用 `requestAnimationFrame` 后再投递 macrotask；恢复流程不 `await` hydration。切 tab 时以 generation/token 取消过期回写。
- `LOADING`：tab 已激活，内容区显示 loading；此时才允许读取 history。普通用户主动打开 conversation 也遵循同一语义：先建立/激活壳，再异步 hydrate，禁止在 `createTab()` 内预取。
- `READY`：小文件沿用旧全量 reader，仅本 tab 投影消息。
- `OVERSIZE_BLOCKED`：任一待读 segment `stat.size > 64 MiB`，该 segment **绝不进入** `readSDKSession()`；显示“超大会话，按需加载将在分页里程碑提供”，列出被阻断 segment 与大小，不把其他成功 segment 冒充完整历史。
- `ERROR`：显示可重试错误；不得标 hydrated。

M1 选择**纯占位**，不提供“最近 98 条/已知 previous segment”按钮。后者来源不完整且会继续强化“98 条即完整历史”的误解；M3 到达后原占位原位升级为分页入口，不产生废弃路径。小于等于 64 MiB 的会话保持现行为。64 MiB 是保守熔断值：远低于 V8 字符串硬上限，并为 `Buffer → string → split → JSON` 多份峰值留出空间；后续只允许根据 Electron 实测下调，不上调来迁就旧 reader。

#### 3. M1 验收

- 隔离 vault 固定 7-tab 恢复 fixture，其中一个 segment 为 1.53 GB sparse/真实冷备；重启后先出现可交互壳，后台 6 tab 的 `getConversationById()` 调用数为 0。

#### 4. 与暂存 v6 的关系

### M2：Worker 索引内核

交付物：抽取共享 chunk reader；在 Web Worker 中按 snapshot size 流式解析轻量 index；主线程只收批次进度/最终索引；segment 返回 `complete|partial|failed`；索引 entry 预留稳定 message key、offset、length、timestamp、branch/tool 关联。`sdkBranchFilter.ts` 规则迁移到 index，并对现有全部 fixture 与旧全量结果逐项对拍。首版索引可内存持有；缓存是后续优化，不阻塞。

验收：>512 MiB、单行 >6 MiB、半行、活跃 append、inode 替换均不构造全文件字符串；Worker 工作期间 UI Long Task <50 ms；branch、顺序、segment 诊断与旧 reader 对拍一致。M2 可上线 shadow 模式，只记录结果而不切 UI；失败自动保留 M1 熔断，不回退旧 reader。

#### M2 开工对齐（v6 × M1 合并后）

1. **external 行进入索引。** 轻量 index 的 `realUser/displayable` 判定必须与 `isDisplayableExternalUser()` 完全同源：`peer | channel | coordinator` 且有稳定 ID、可提取正文的 user 行，即使 `isMeta: true` 也保留；`task-notification` 不作为可见 user turn。`extractExternalDisplayContent()` 本身只做字符串/字段处理，但当前位于 `ClaudeTranscriptTurnMapper.ts`，该模块顶层还依赖 runtime/stream transform；Worker 不直接 import 整个 mapper。开工时把 `extractExternalDisplayContent`、`isDisplayableExternalUser` 及 external kind 常量抽到 history/transcript 均可引用的纯模块，`sdkMessageParsing.ts`、`sdkBranchFilter.ts`、mapper 和 Worker 共用，禁止复制判定。

2. **索引只同构 turn 边界，不同构 assistant 投影。** Worker 不实现 assistant 连续实例聚合、同 id 隔离、terminal-candidate 或 stop-hook 续写；这些仍由 materialize/投影层处理。索引在 canonical branch 上仅以“普通 real user 或上述 displayable external user”开启新的可见 turn，记录 `turnId = uuid ?? origin.msg_id`，后续 assistant/tool/system 行归当前 turn，直到下一个可见 user；隐藏 external/task-notification 不新开可见 turn。该边界以当前 history 可见性与 mapper 的 external 分类为准。

3. **Worker 与 observer 独立消费并显式交接。** 两者各持 file handle、offset、partial buffer，读取互不改变对方位置；Worker 固定启动时 `dev/ino + snapshotSize`，只索引 snapshot，observer/tail 只消费其后的 append，inode 变化或缩短均使索引失效并重建。1.5 GB 扫描不是持续“双倍全文件读取”（observer 通常只读增量，恢复扫描上限 4 MiB），但仍有磁盘带宽竞争；Worker 使用有界 chunk、批次让步与单文件单任务去重，并以 observer tick p95、UI Long Task 和索引吞吐做真机验收，不能仅以“在线程外”判定无影响。

触发保持 M1 语义：首次激活 tab、首帧后才启动；M2 shadow 对超限会话仅建索引并保持 `OVERSIZE_BLOCKED`，不提前创建 runtime/observer。小会话仍走旧 hydration，可并行产出 shadow 对拍。M3 接管后，索引完成并 materialize 首页，再创建 runtime/observer，并从已确认的 snapshot boundary 补消费 append，确保不漏不重。M2 首版仅做进程内、按 `absolutePath + dev/ino + snapshotSize + mtime` 的 in-flight/完成索引复用；持久化缓存仍为后续优化，不阻塞开工。

## 四、每批实施纪律

每个里程碑按同一流水线执行：

1. **红测先行**：先提交能稳定复现该批失败的最小测试；确认测试在改代码前失败，禁止先写实现再补测试。
2. **实现与定向绿测**：只改该里程碑文件，先跑对应 Jest project/path。
3. **全量门**：`npm run typecheck && npm run lint && npm run test && npm run build` 全绿；branch 相关批次必须额外跑全 fixture 对拍。
4. **隔离部署验证**：复制真实 transcript 到隔离 vault；记录启动首帧、Long Task、读取字节、峰值 RSS、首屏/翻页耗时。不得在用户生产 vault 首次验证。
5. **逐批部署与回滚点**：每批独立构建、独立部署、保留上一产物；验收失败回滚本批，不跨里程碑夹带修复。

# 风险与权衡

1. **当前观测的“较近部分”无法仅由静态代码精确还原来源**：代码实证只能确定 1.53 GB 当前 segment 整体失败，不会自然返回其尾部 N 条。可见部分可能来自 8.76 MB previous segment、重载后新增消息或重载前残留状态。实施前应加 segment 级诊断日志确认来源。
2. **branch 正确性优先于“从尾部倒读”**：简单 reverse-tail 会漏祖先、跨页 tool result 和非 user sibling；必须先有轻量全局索引。
3. **超大单行**：真实单行达 6.84 MB，chunk reader 要支持跨 chunk 聚合；上限必须显式且可诊断。
4. **活跃文件一致性**：索引期间 transcript 仍追加。以开始 size 作为 snapshot boundary；完成后再消费 append delta，避免读到半行或 branch 图前后不一致。
5. **subagentData 膨胀**：78.9 MB metadata 本身已不合理。应另立后续项，将持久化内容收缩为状态/引用，详细 tool calls 从 sidecar 按需加载；本方案第一期至少不得复制它多份。
6. **交互语义**：对未加载历史执行搜索、fork、rewind 时，要么先定位并加载目标页，要么明确提示；不能把“未加载”误判成“不存在”。
7. **迁移代价**：虽为务实方案，仍涉及 provider history contract、Claude parser/index、ChatState 与 renderer；但只修 reader 会很快在 DOM 和内存层再次失败，不能作为长期结论。
