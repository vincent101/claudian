# 背景与问题

核实 Claudian 3.1.0（`f65efba5`）四项留档问题的真实性与触发面，并只为确需修复项给出不破坏历史快照、分支截断和 projection FIFO 语义的最小方案。

# 方案设计

## 结论总览

| 项 | 真伪 | 触发面 | 裁决 |
|---|---|---|---|
| P1 refresh 持 stored grant 重扫 | 真 | 搜索面板存在非空查询时的流完成；首次非空查询与 Retry 也会 refresh。文件快照变化时重扫 | 修 |
| P2 completed cache 不区分 resume | 真，且 fork 主路径可达 | fork 创建后首次水合直接带 resume，但源会话普通索引通常已在全局 completed cache | 修，优先级最高 |
| P3 pageKey 未落盘 | 真 | `memory_only_rematerialize`、`page_render_timeout`、`dom_overcommit` 三类均丢 pageKey | 修，但只落哈希 |
| P4 后缀扫描器重复 key 语义 | 清单前提为假 | 右向扫描首次命中即最右值，恰与 `JSON.parse` 的后值覆盖前值一致；正常 SDK `JSON.stringify` 行不会生成重复键 | 不修 |

## P1：缩小 stored 临界区，不在 grant 内等待索引

### 证据与量化

- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/controllers/ConversationController.ts:638-674` 在 `runStoredTransaction` 内创建强制新快照并 `await next.ready`，期间 `ProjectionWriteCoordinator` 的独占 grant 不释放。
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/rendering/ProjectionWriteCoordinator.ts:47-64,113-161` 对 live/stored 共用同一 FIFO 独占队列；因此后来的 live turn 必须等 refresh 完成。
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/controllers/HistorySearchController.ts:183-185,195-235,251-272` 表明 refresh 只在搜索面板有非空查询时由流完成触发，或在每次打开后的首次非空查询、Retry 触发；不是每个普通 turn 都触发。
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/controllers/StreamController.ts:348-356` 在收到 `done` 时同步发出 `onStreamComplete`；`InputController.ts:744-750` 稍后才释放 live projection lease。refresh 因而先排在 FIFO，live 释放后取得 grant；紧接着的新消息再申请 live 时排在 refresh 后。
- 真机 `history-render.current.jsonl` 仅有 1 次 `search_snapshot_refresh`：`rebuilt` 1/1，耗时 1192.3 ms。它对应 `history-index.current.jsonl` 对 167,262,550 B 文件的 direct 重扫，complete 1185.8 ms。样本只有 1，不能把 100% 外推成长期概率。
- retained current+previous 中共有 78 次 index complete：p50 603.3 ms、p90 4251.7 ms、p95 14170.9 ms、最大 65064.3 ms；最大样本扫描 1,640,331,690 B。56/78 小于 1 s，7/78 不低于 10 s，3/78 不低于 20 s。这不是 refresh 专属分布，但给出了同一构建器可能占用 grant 的实测量级。
- 代码没有构建超时，耗时随文件、I/O 和 direct-build 排队增长，故不存在有限“真实时长上界”；可陈述的只有当前留档最大 65.1 s。
- 无 deadlock 环：refresh 等 `next.ready`；索引构建不申请 projection lease，stream completion 也不 await refresh；live lease随后在 finally 释放。当前问题是有界于构建完成/失败/abort 的队头阻塞，不是循环等待。

### 推荐结构

改 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/controllers/ConversationController.ts:610-677`：

1. 在 stored grant 外捕获 `conversationId`、`previous`，调用 `acquireLease(..., forceNewSnapshot=true, reportProgress=false)` 并等待 `next.ready`。
2. 构建期间旧 lease 继续挂载且保持保护；paging/search locate/live turn 可继续通过既有 FIFO 使用旧快照。
3. `next.ready` 成功后，仅把“重新校验 → swap → release previous”放进 `runStoredTransaction`：
   - conversation 已切换、mounted lease 已变化：release `next`，返回 stale；
   - 否则先 `state.historyLease = next`，再 `previous.release()`。
4. 失败时只 release 未挂载的 `next`，旧 lease 保持可用；沿用现有 failed 诊断。
5. 不改 `ProjectionWriteCoordinator`，也不引入第二套锁。现成 stored FIFO 已足以原子化交换；难点通过缩小临界区消失。

此结构保留 F5 的核心不变量：窗口任务只会在 grant 内捕获 lease；交换也只在 grant 内发生，因此不会使用已释放 lease。代价是 refresh 构建期间搜索/分页仍看到旧快照，直到原子交换完成；这是比阻塞新 turn 更合适的一致性取舍。

### 测试

在 `/Users/vincentwang/Documents/NoteVault/tools/claudian/tests/unit/features/chat/controllers/ConversationController.test.ts` 调整/新增：

- `next.ready` 悬挂时，新的 live lease 能取得并释放，不被 refresh 构建阻塞。
- 构建期间 paging 可用 previous；构建完成后交换排在当时持有的 live/stored 工作之后。
- paging 若在交换后取得 grant，只捕获 next。
- 构建期间 switch：next 完成后被释放，不复活旧会话。
- 构建失败：next 释放、previous 保持挂载。
- 明确验证 refresh 不等待任何 live 结果，排除锁环回归。

## P2：把 resume 语义纳入 completed 与 in-flight cache identity

### 证据与后果

- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/ClaudeTranscriptHistoryIndex.ts:1366-1382`：request cache 已含 `resumeAtMessageId`，但 snapshot resolved 后，`completed` 与 `inFlight` 都只按 `filePath/dev/ino/size/mtimeMs` 命中。
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/ClaudeConversationHistoryService.ts:282-308` 确实把当前 segment 的 `forkSource.resumeAt` 传给 `buildTranscriptIndex`。
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/tabs/TabManager.ts:857-910` 先持久化带 `forkSource.resumeAt` 的新 conversation，再 `createTab` 或 `switchTo`；`ConversationController.loadActive/switchTo` 首次水合本身直接带 resume，不存在“fork conversation 先普通建、再 resume 建”的内部时序。
- 但 source conversation 通常已被当前 tab 普通水合，且其 completed entry 因 active lease 受保护。因此 fork 首次 resume 构建会命中源文件同快照的普通 completed cache。触发不依赖 fork 内部先普通后 resume；它跨 conversation 复用全局 cache，正常 fork 路径即高概率可达。
- 反向同样错误：若 resume 版本先入 cache，之后普通读取可能拿到被截断索引。
- 后果：`finalizeIndex(..., resumeAtMessageId)` 被整体跳过，既不会按 checkpoint 截断，也不会执行 oversized ancestry 的 fail-close。fork 水合可显示 rewind 点后的消息；若 opaque oversized 行缺 uuid/parentUuid，本应失败的 resume 会静默成功。

### 推荐修法

改 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/ClaudeTranscriptHistoryIndex.ts:1008-1059,1366-1433`：

- 定义单一 cache identity helper：`snapshot identity + projection variant`；variant 至少包含 `resumeAtMessageId ?? none`。
- `completed` 与 `inFlight` 必须使用同一 composite key；不能只修 completed，否则普通与 resume 并发仍会共享错误构建。
- `requests` 现有 key继续保留；可复用统一 variant 编码，避免三套 key 规则漂移。
- 不推荐“resume 一律绕过 cache”：正确但会让同一 fork 的多 lease/重开重复扫描超大 transcript，也未自然解决 plain/resume in-flight 污染。

cache entry 数可能从“每个文件快照一个”增为“每个文件快照、每个 resume anchor 一个”；现有全局 8 项/128 MiB LRU 继续提供上限，无需另建 cache。

### 测试

在 `/Users/vincentwang/Documents/NoteVault/tools/claudian/tests/unit/providers/claude/history/ClaudeTranscriptHistoryIndex.test.ts` 增加：

1. 同文件同快照先 plain 后 resume：resume 不 `fromCache`，结果截断到 anchor。
2. 先 resume 后 plain：plain 不复用截断结果，返回完整索引。
3. plain 已缓存后，对含不可验证 oversized ancestry 的同快照做 resume：仍 `failed`。
4. 相同 snapshot + 相同 resume 可命中 cache。
5. 同快照 plain 与 resume 并发时不共享 `inFlight` promise。

在 `/Users/vincentwang/Documents/NoteVault/tools/claudian/tests/unit/providers/claude/history/ClaudeConversationHistoryService.test.ts` 保留一条集成级断言：source conversation 已普通 acquire 后，fork conversation acquire 得到 checkpoint 截断状态。

## P3：补齐 feature→持久诊断映射，但不落原始 pageKey

### 证据

- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/history/HistoryDiagnostics.ts:12-29` 的三类事件携带 pageKey：`page_render_timeout`、`dom_overcommit`、`memory_only_rematerialize`。
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/main.ts:75-84` 三条路由均未转发 pageKey；memory-only 只写 phase。
- 当前 `history-render.current.jsonl` 没有 `memory_only_rematerialize` 实例，故不能用真机现有样本观察该事件；但路由是确定性字段丢弃。现存日志也没有 pageKey 字段。
- `TranscriptDiagnosticEvent` 自身所有已声明字段都在 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/transcript/ClaudeTranscriptDiagnosticLog.ts:92-97` 白名单内；“同类静默丢字段”发生在 feature union 到 provider log 的适配层，而非该接口对白名单。逐项对照后，额外丢失仅为上述三类的 pageKey。
- pageKey 对窗口页通常包含 transcript 绝对路径与 stat identity（`ClaudeConversationHistoryService.ts:597-620`），不能原样写诊断。

### 推荐修法

1. 在 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/transcript/ClaudeTranscriptDiagnosticLog.ts:18-47,92-97` 增加 `pageKeyHash?: string` 并纳入白名单。
2. 在 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/main.ts:75-84` 对上述三类事件统一写 `pageKeyHash: renderDiagnostics.hashId(event.pageKey)`。
3. 不把 `pageKey` 原文加入持久类型，避免路径泄露；沿用日志实例盐化、12 位 hash 的现成机制。

成本小，但能把不变量破坏/超时/DOM 过载关联到同一页，值得修。

### 测试

- `/Users/vincentwang/Documents/NoteVault/tools/claudian/tests/unit/providers/claude/transcript/ClaudeTranscriptDiagnosticLog.test.ts`：`pageKeyHash` 落盘，原始 pageKey/路径不落盘。
- main 组合层测试：三类事件均转发同一字段映射；防止以后 union 新增字段后再次静默丢失。优先把映射抽成一个可穷尽 switch 的纯函数并以 `never` 保证新增 kind 编译失败，而不是继续维护开放式 if/else。

## P4：维持实现与测试，只纠正留档结论

- JavaScript 实测 `JSON.parse('{"uuid":"left","uuid":"right"}').uuid === 'right'`。
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/ClaudeTranscriptHistoryIndex.ts:535-590` 从右向左扫描，同一尾窗内第一次看到的是最右 key，之后因字段已定义而忽略更左者，正好符合 `JSON.parse` 后值覆盖前值语义；现有注释正确。
- prefix 扫描取最左；当超大行的两端窗口分别看到冲突值时，`mergeOversizedLineFacts` 在 `:610-647` 降级为 unknown/conflict。这比模拟重复键覆盖更保守，专用于不完整双窗事实合并。
- 正常 CC 行由对象单次 JSON 序列化产生，不会出现同一对象重复顶层键；现有测试也明确以手写 raw JSON 构造防御场景。因此业务路径不可达，手工篡改/损坏文件仍由 conflict 防御覆盖。

裁决：不改代码、不改注释、不加断言。现有手写 duplicate-key 测试已经是所需防御证明；新增运行时断言只会把可降级的外部损坏升级为构建失败。

## 实施分批与档位

1. **批 A：P2（正确性）**。`implementer-high`；索引 cache identity 与两层测试，单独提交，先消除 fork 数据错误及 fail-close 绕过。
2. **批 B：P3（可观测性）**。`implementer-lite`；若采用“穷尽纯映射函数”则 `implementer-high`。可与 P2 同发布但建议独立提交。
3. **批 C：P1（并发结构）**。`implementer-max`；独立提交，必须做并发时序测试与 reviewer 复核。不要与 P2 混改，便于归因。
4. P4 不实施。

# 风险与权衡

- P1 将“refresh 开始即阻塞所有 projection 写”改为“后台构建旧快照可继续服务，完成后短临界区交换”。一致性从强阻塞改为显式旧读；搜索本来就在 refresh 成功前使用旧 snapshot，语义一致。
- P1 构建完成后若 live turn已先取得 grant，交换会等该 turn 完成；这避免中途替换 lease，是必要等待，不是原问题。
- P1 的 65.1 s 是现有留档最大值，不是理论上界；当前诊断无法直接统计“live 被 refresh 阻塞多久”。若要上线后量化收益，应给 projection coordinator 增加按 work kind 的 queueMs，但不纳入本次最小修复。
- P2 增加 cache variant 数量，可能提高 LRU 淘汰率；有 8 项/128 MiB 硬上限，正确性优先，且绕过 cache 的替代方案代价更差。
- P3 必须存 hash 而非原始 pageKey；否则窗口 pageKey 会泄露本地 transcript 路径。
- 待用户确认：是否接受 P1 构建期间搜索/分页继续读旧快照。推荐接受；否则只能维持当前最长可达数十秒的全队列阻塞。

人工/真机验收：

1. 打开大 session 的搜索面板并保持非空查询，让一轮输出结束后立刻发送下一条；thinking indicator 应立即启动，refresh 最终仍记录 rebuilt/cache_hit。
2. 在源会话较晚位置创建 fork；fork 首屏与搜索均不得出现 checkpoint 后消息。
3. 用 oversized ancestry fixture 验证 plain cache 已存在时 resume 仍 fail-close。
4. 触发三类 page 诊断，确认日志有稳定 `pageKeyHash`、无原始路径。
5. 对比 `history-render` 的 refresh elapsed 与新增 coordinator queue 指标（若另行加入），确认重扫耗时不再转化为 live queue 等待。
