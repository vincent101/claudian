## 背景与问题

B1 把存量消息改为分帧投影，但存量队列、流式增量和搜索定位重建仍各自写同一 `messagesEl`；同时，锚点 turn 的“必须存活”被错误实现为字符预算豁免，导致两个边界都不封闭。

### 问题机制图

```text
顺序错乱
hydrate/loadActive ── renderMessages: 首片同步、后片排队 ───────┐
                         │ READY 提前                         │
用户 send ── addMessage(user/assistant) ──────────────────────┤→ 同一 messagesEl
                         │                                    │
下一帧旧队列继续 append ─────────────────────────────────────┘
结果：新 turn 插在旧历史中间。

流式失联
stream chunk ── ChatState/TurnProjectionContext 更新（真相）
            └─ currentContentEl 写 DOM（投影）
Cmd+F 未加载命中 ── loadWindow ── renderMessages.empty() ── 新 DOM
旧 currentContentEl 已脱离 DOM，后续增量仍写旧节点 → 界面不再更新。

预算越界
materializeWindow ── newest-first ── newest/anchor 豁免准入检查
                                  └─ summarize 后仍可能 > maxProjectedChars
```

根因不是单个缺失的 `await`，而是：

1. `MessageRenderer.renderGeneration` 只协调存量队列，不覆盖流式写入。
2. `waitForRenderedMessages()` 仅返回调用时的 promise；若等待期间发生 supersede，旧 promise 提前 resolve，不能表达“当前所有存量写入已空闲”。
3. `READY` 表示数据/运行时可用，却被发送路径当成 DOM 已稳定；两种就绪语义混用。
4. `currentContentEl` 是易失投影引用，搜索清空 DOM 后没有失效检测或由 `ChatState` 重投影。
5. `isNewest` 同时承担“锚点不可丢”和“预算可豁免”，混淆了生存性与大小约束。

## 方案设计

### 一、补修 1：流式与存量分帧的互斥/排空协议

#### 1. 方案选型

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 仅在发送前等待 | `sendMessage` 调 `waitForRenderedMessages()`；流式时禁用搜索定位 | 改动最小 | 检查与异步加载间仍可竞态；现有 waiter 可被 supersede 提前释放；未来调用方易漏 | 不选 |
| B. 每 tab 投影写租约 + DOM epoch | 存量事务和完整流式 turn 互斥；清空型重建递增 epoch；失效时只写 domain，结束后重投影 | 边界清晰；顺着 domain-first；覆盖三类写入；Provider 无关 | 增加一个小型协调器及接线 | **推荐** |
| C. 流式中即时重建并热迁移全部 DOM 状态 | 搜索可立刻跳转，同时重建 text/thinking/tool/subagent 节点 | 体验最即时 | 必须迁移多类 renderer 私有状态，容易重复渲染、丢 tool 状态；回归面大 | 务实补修不选 |

#### 2. 协议不变量

新增每 tab 一个 `ProjectionWriteCoordinator`，只协调“ChatState → messagesEl”投影，不接管 provider/runtime：

- **P1 单写者**：`stored` 租约（清空重建、prepend 分帧）与 `live` 租约（一个完整流式 turn）互斥；同类事务 FIFO 串行。
- **P2 live 边界**：发送在创建 user/assistant DOM 前取得 `live` 租约；直到流式 finalize、DOM flush 完成才释放。未加载搜索定位和分页在此期间等待，不清空 DOM。
- **P3 stored 原子性**：搜索定位的 `loadWindow → 合并 ChatState → renderMessages → 等待当前队列排空` 属于同一个 `stored` 事务，不能只锁最后一次 render。
- **P4 epoch 校验**：每次 `renderMessages` 清空重建时递增 `domEpoch`；流式 context 捕获 epoch。每个 chunk 投影前同时校验 epoch 与 `messagesEl.contains(renderTarget)`。
- **P5 domain-first**：epoch/挂载校验失败时，chunk 仍完整更新 `ChatMessage`、`contentBlocks`、`toolCalls`、subagent domain state，只跳过 DOM；标记 `projectionDirty`。turn 结束后从 `ChatState.messages` 做一次受 `stored` 租约保护的全量重投影。
- **P6 READY 含义**：tab 进入 `READY` 前，初始 `renderMessages` 队列必须排空。`READY` 此后表示运行时与首屏 DOM 均可交互。
- **P7 无超时放行**：互斥与排空按条件完成，不用定时器猜测；tab 关闭/代际失效通过取消 token 释放等待者。

#### 4. 协议时序

```text
初始加载：stored render → drain → runtime ready → hydration READY
发送：    reserve live → await prior stored/drain → revalidate → append user/assistant
流式：    live lease 持有；chunk 先写 domain，再经 epoch/mounted 校验写 DOM
搜索：    loaded hit 直接定位；unloaded hit 排队等待 live release
结束：    finalize/flush → release live → queued stored search 合并最新 ChatState 并重建
异常：    epoch 变化/节点脱离 → DOM 停写、domain 继续、dirty=true → turn 后完整重投影
```

#### 5. Codex 兼容性

该协议位于共享 chat feature，只依赖 `ChatState`、`MessageRenderer` 和 provider-neutral `StreamChunk`，Claude 与 Codex 走同一路径。不得在 coordinator 中读取 `providerId` 做分支。Codex 的 provider message boundary 会更换 active assistant message；每次 boundary 只刷新同一 live lease 下的 target/epoch，不另开租约。Claude 专属的分页 API 只决定哪些 stored 事务会发生，不改变协议。

### 二、补修 2：anchor turn 的 projectedChars 硬上限

#### 1. 设计

在 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/HistorySummaryProjection.ts` 新增纯函数 `hardCapChatProjection(messages, maxProjectedChars)`（名称可按实现风格调整）：

- 输入先经过现有 `summarizeChatMessages`；仅当再次测量仍超限时进入二次压缩。
- 保留 `ChatMessage` 的 id、role、timestamp、provider 原生消息 id 与数组顺序，即“锚点 turn 存活”；只裁剪投影载荷。
- 按确定顺序压缩所有被 `measureChatProjectionChars` 计数的表面：`content/displayContent`、文本/思考 block、tool result、tool input 字符串与结构化输入；删除 images、diff、嵌套 subagent tool detail 等摘要层非必要字段。
- 文本使用预算感知的 head/tail 截断并加入明确省略标记；若剩余预算小于完整标记，标记本身也截至剩余长度。最终兜底可清空可计数字段，但不删除消息壳或 turn range。
- 函数返回 `{ messages, projectedChars, truncated }`，并以 `measureChatProjectionChars(messages) <= maxProjectedChars` 为后置条件；`maxProjectedChars < 0` fail-fast。

修改 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/ClaudeConversationHistoryService.ts`：

- 每个 produced turn 在摘要后重新测量；若单 turn 超预算，调用 hard cap，再重新测量。
- `isNewest` 仅豁免“是否纳入窗口”的累计准入判断，不再豁免单 turn 硬上限。
- 因此 newest/anchor 始终至少保留消息壳与省略说明，但 `chars <= budget.maxProjectedChars`；旧 turn 仍按累计字符/字节预算停止。
- `projectedChars` 与 diagnostics 使用二次压缩后的真实值，不做 `Math.min` 伪装。

#### 2. 不变量

```text
非空计划 ⇒ anchor turn 的消息身份仍在结果中
任意窗口 ⇒ page.projectedChars == measure(page.messages)
任意窗口 ⇒ page.projectedChars <= budget.maxProjectedChars
截断 ⇒ 有可容纳空间时必须出现明确省略标记
```

## 风险与权衡

1. **搜索等待时延**：未加载命中的定位会等当前流结束；这是务实选择，优先保证不丢增量。搜索面应显示“响应完成后定位”，避免像卡死。
2. **锁顺序**：固定为业务 turn lease → live projection lease；live 释放后才可申请 stored。任何反向顺序都可能死锁，需在 coordinator 注释与测试中固化。
3. **取消与 stale 请求**：tab close、切换、hydration generation 变化必须取消排队项；否则旧搜索可能在新会话释放锁后重绘。
4. **异步 Markdown 渲染**：projection lease只覆盖消息节点结构和流式挂载点，不等待每个普通 Markdown job；后者已有 per-message content generation。不得把两类等待合并成全局长锁。
5. **硬截断语义**：二次截断会降低极端 turn 的可读性，但不改变 domain/transcript，也不删除锚点；这是硬资源上限与完整展示之间的必要取舍。
6. **`status: proposed`**：按本次派单要求记录；与仓库既有 `draft/confirmed/superseded` 枚举不一致，后续若有自动校验需同步确认状态词口径。

### 验收标准

- 任意时刻只有一个 stored 事务或一个 live turn 可写 `messagesEl`；无超时放行。
- 1.59GB 会话首屏分帧中立即发送，DOM 顺序与 `ChatState.messages` 一致。
- 流式中 Cmd+F 未加载命中不会清空活跃挂载点；响应结束后能定位，期间所有增量保留且可见。
- Claude、Codex 的发送/流式/provider boundary 回归测试均通过，无 provider 特判。
- 所有 history window 满足 `projectedChars <= maxProjectedChars`，且锚点 turn 不被删除。
- 执行：`npm run typecheck && npm run lint && npm run test -- --selectProjects unit && npm run build`。
- 人工复测：超大会话首屏立即发送；流式文本/工具调用/子代理阶段分别触发未加载搜索定位；切 tab/关闭 tab 取消等待；核对无重复、乱序、隐形增量和永久等待。
