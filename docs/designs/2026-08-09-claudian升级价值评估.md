# Claudian 2.0.11 → 2.1.2 升级价值评估

> 调研性质：这不是设计方案，是一份供决策的评估报告。结论先行，分类清单在后。
> 调研日期 2026-08-09，本地 2.0.11（含 5 个手工 patch），上游最新 release 2.1.2（2026-08-05），main 分支领先 2 个 commit（#1070 文件树、#1071 tab 构造重构）。

## 一句话结论

**建议：留守 2.0.11，观望，等"刺痛升级"。** 当前净价值为负——升级换来的功能里，对一个已自建五色灯语的重度用户而言，唯一有实际痛感的是 AskUserQuestion "Other" 不可达的 bug；而升级会直接且不可逆地摧毁你已有的全部定制能力（minify），并强迫放弃"review 与 action-required 分色"这个你超出上游的定制。

**升级触发条件（满足任一即重新评估）**：
1. AskUserQuestion 的 "Other" 选项让你频繁受阻（这是 2.0.11 唯一的实质功能缺陷）
2. 你想用 dual-pane 会话管理
3. 某个未来的上游版本出了你真正需要、且无法绕过的能力

## 关键事实（全部有据，可在文末速查复核）

### F1. 升级区间：2.0.11 → 2.1.2 共 34 个版本

2.0.12（05-13）至 2.1.2（08-05）。中间无 2.0.35（跳号）。release notes 已逐版读完（见文末附录）。

### F2. 致命约束：minify 边界在 2.0.34 → 2.0.36

实测下载两版 release 产物对比：

| 版本 | 行数 | 平均行长 | `function supportsXHighEffort` | 结论 |
|---|---|---|---|---|
| 2.0.34 | 110331 | 39 | 存在（1 处） | **未压缩** |
| 2.0.36 | 881 | 3165 | 不存在（0 处，已 mangle） | **已压缩** |

**含义：升到 2.0.36 或更高，你现有的 5 个 patch 的锚点全部失效，且未来任何 bundle patch 都不再可行**（函数名 mangle、局部变量重命名、`setupServiceCallbacks` 等挂载点消失）。届时唯一定制路径是 fork 源码自建——成本远高于现在的 patch。这是不可逆的代价拐点。

### F3. 你的 xhigh patch = 上游 2.0.28 自己的修复，逐字节同源

本地 2.0.11 你加的 `main.js:55733`：
```js
if (isBuiltInFamilyVariant(normalized, "sonnet")) return true;
```
上游 2.0.28（#853）在 `src/providers/claude/types/models.ts:97` 加了**完全相同的一行**。你预判了上游的修复方向。此 patch 升级后无损（上游 2.1.2 已重构为配置表，`modelTiers.ts:34` sonnet `aliasSupportsXHigh: true`）。

### F4. 你的 attention patch 与上游 2.1.0 的 attention 状态机：功能等价，但你赢了分色

上游 2.1.0 才引入 attention（2.0.44 及以前 `beginActionRequired`/`markReviewRequired` 全为 0 命中，已逐版 grep 验证）。但上游把 **review 和 action-required 渲染成同一个 `.claudian-tab-badge-attention` 色**（`tabs.css:93` 只有这一个类，`TabBar.ts:79` 只判 `needsAttention`，无 review 专属类）。

你的方案做了**分色**：红=等回答、黄=待检查。这是**本地超出上游的定制，升级即丢**。除非 fork 改源码，否则拿不回。

### F5. dual-pane 默认开启（2.1.x `enableDualPane: true`）

`defaultSettings.ts:56`。可在设置里关，但这是真实 UI 变化：左侧多出一个会话管理面板。2.1.1 又加了可配置布局，2.1.2 连修两个 sidebar 布局 bug——说明 2.1.0 的布局改动有反复，尚在稳定期。

## 分类评估

### A. 与本地 patch 重叠的（升级能替代 vs 会丢失）

| 本地 patch | 上游对应 | 升级后 |
|---|---|---|
| xhigh（sonnet） | 2.0.28 #853 → 2.1.2 配置表 | ✅ 无损替代（F3） |
| attention（红=等回答） | 2.1.0 attention 状态机（action-required） | ✅ 能替代，且上游引用计数更严谨 |
| review（黄=待检查） | 2.1.0 review 状态 | ❌ **丢失分色**——上游 review 与 action-required 同色，无独立黄（F4） |
| streaming 换绿 | 无对应 | ❌ 丢失（上游 streaming 仍是 brand 色） |
| 5 色整套灯语 | 无对应 | ❌ 丢失（上游最多 4 态、review/action 合并） |

**净判断**：升级后你只能回到"蓝=当前 > 红/默认色=attention(等回答+待查看合并) > 绿?不，是 brand 色=运行 > 灰=空闲"。**等回答与待查看被迫同色，streaming 色也回退**。你的五色体系塌缩成上游的三到四态。

### B. 新增且有实际价值的功能

按对你的价值排序（信贷分析师、多 tab 并行、subagent、plan、AskUserQuestion 高频、xhigh）：

| 版本 | 功能 | 对你的价值 |
|---|---|---|
| 2.1.0/2.1.1 | **dual-pane 会话管理** | 中。多 tab 重度用户可能受益，但你已有 8 tab 工作流，且它默认改变布局 |
| 2.0.43 | **plan 模式可用于新会话**（#1018） | 中。你用 plan 模式，2.0.11 在新会话里 plan 可能不可用 |
| 2.0.19 | **渲染 markdown 于 inline edit 预览**（#714） | 低-中。改善编辑预览可读性 |
| 2.0.15 | **可配置发送快捷键**（#643） | 低。默认 Cmd/Ctrl+Enter 已够用 |
| 2.0.42 | **流式 markdown 渲染协调**（#989, perf） | 低-中。长流式输出更顺滑，重度使用有感 |
| 2.0.40 | 窄侧栏 toolbar 换行（#956） | 低。你用 right-sidebar（默认值，未改），窄侧栏时权限/模式选择器不再被挤掉 |
| 2.0.28 | Fable 5 选项 | 低。除非你买了 Fable |

其余多为 Pi/Codex/Grok/OpenCode provider 相关（你不用）或纯重构/测试/文档（无运行价值）。

### D. 破坏性变化 / 风险

1. **minify（F2）**——最大风险。2.0.36 起不可再 patch。你的全部定制能力与未来定制能力一次性终结。
2. **review 分色丢失（F4）**——你超出上游的核心定制，升级即塌缩。
3. **dual-pane 默认开启（F5）** + `tabBarPosition` 设置项移除（2.0.25 #793 移除）——UI 布局变化，tab badge 位置/显隐逻辑改变。2.1.2 仍在修 sidebar 布局，稳定期未过。
4. **8 个已打开 tab 的恢复**——跨 34 版，data.json 里的 `tabManagerState` 迁移未亲测，有回不去的风险（虽有回滚手段）。
5. **你的 5 个 patch 与上游同区改动冲突**——上游在 2.0.25/2.0.33/2.1.0/2.1.1/2.1.2 都动过 badge/CSS 区，即便忽略 minify，手工合并也易错。

### E. "只有升级才能拿到"的清单（minify 阻断 backport）

这些在 2.0.11 上**无法靠 patch 获得**，是真正的升级拉力：

1. **dual-pane 会话管理**——整套 UI + 状态，不可能 patch 进 2.0.11
2. **AskUserQuestion "Other" 修复**——理论上能 backport（2.0.11 未压缩），但需复刻 #675 的 24 行改动 + ClaudeApprovalHandler 的 isOther 注入，工作量不小
3. **plan 模式用于新会话**（#1018）
4. **环境变化保留历史**（#981，对你频繁切模型有感）
5. 各类 provider 新功能（你不用）

**关键判断**：除 dual-pane 外，其余"升级独占"项**要么价值中等，要么理论上可 backport**。没有一个是"非升级不可"的刚需。

## 最终建议：留守，观望

**理由（net value）**：
- **得到的**：一个中等价值的 dual-pane、几个中等 bugfix（Other、环境保留历史、首轮 rewind）、一堆 provider 功能（不用）
- **失去的**：五色灯语（review 分色是你超出上游的定制）、全部 patch 能力（minify 不可逆）、当前稳定的 8 tab 工作流手感
- **代价**：dual-pane 默认改布局、跨 34 版的迁移风险、2.1.x 布局 bug 尚在修

对一个已经把状态灯语打磨到五色的用户，这套交换明显不划算。

**观望期间盯两件事**：
1. **AskUserQuestion "Other" 若频繁受阻** → 这是唯一值得认真考虑 backport 的点（2.0.11 未压缩，可 patch）；backport 不了或嫌烦，再谈升级
2. **上游何时把 review 分色做了**——若未来版本给 review/action-required 分色（或暴露 per-kind 的 CSS 钩子），升级的最大障碍消失，可重新评估

**若哪天决定升级**，唯一正确姿势是：fork 源码 → 在源码层重做五色分色（改 `tabs.css` + `TabBar.ts` 渲染分支）→ 自建产物 → 部署。届时 minify 不再是障碍（你有源码）。不要试图在 minified 产物上 patch。
