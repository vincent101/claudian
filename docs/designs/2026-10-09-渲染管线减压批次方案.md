# 渲染管线减压批次方案（[务实]：止血优先 + 结构分期）

## 背景与问题

2026-10-09 ailoan 会话（36351190）实证三症状：①会话转圈无输出（transcript 已落但 UI 不渲染）②搜索面板长期"索引中"③主线程高占用。根因两条：

- **A. 大消息超重循环**：单条 tool_result 达 2.8MB 级（TaskOutput 大结果）。诊断 `history-render.previous.jsonl` 25 分钟内 `page_data_overcommit` 1330 次（峰值 379 次/分钟，相邻事件中位间隔 1ms）。**本次设计补充判读**：全部事件 `entries=1`（非 live 常驻页恒 1 个、408KB–1.4MB）→ 超重主体是被诊断排除在计数外的 **live 页自身**——单轮内累积多条 MB 级 tool_result（赋值发生在流式期间，`msg.toolCalls[].result` 无界增长），freeze 时 `JSON.stringify(messages)×2` 一次算出 32MiB+ 权重；胖页保持 mounted 且无 victim（live/memory-only/mounted 均豁免驱逐）→ 此后每个 scroll 采样帧的 unpin→enforceLimits 都重发诊断（含主线程同步 `appendFileSync`）。
- **B. refresh exchange 无限排队**：`search_snapshot_refresh` elapsedMs=1,982,647（33 分钟）。索引 build 本身亚秒级；卡点是 `refreshHistorySearchSnapshot`（ConversationController.ts:630-706）末尾的 `runStoredTransaction` 交换——在 projection grant FIFO 里排在被 Stop hook 拖长的 live turn 之后。

三个子项各自独立 TDD、可独立部署；交付顺序 **2→3→1**（复核订正：子项 1 非独立止血，并入子项 3 批次收尾）；子项 3 最重，交付后需独立复核（派单要求）。诊断节流按用户裁决不做，不在本批范围。

### 派单假设的实证修正（设计前提对齐）

1. **live 页更新链没有逐 chunk upsert**（已核验全部调用点）：upsert 只发生在 `beginLivePage`（turn 开始，携带 `[userMsg]`）与 `freezeLivePage`（turn 结束，携带 `[userMsg, assistantMsg]`）——InputController.ts:455/775、AutoTurnProjectionController.ts:148/430。派单设想的"逐 chunk 追加热路径"不存在；真热点是 freeze 一次全量 stringify + 流式期间数据层无界增长。
2. **`runStored` 无超时能力**（已读 ProjectionWriteCoordinator.ts）：acquire 仅在 grant / 排队时 isCancelled 命中 / dispose 时 settle，无退出等待机制 → 子项 2 需在 coordinator 加。
3. **搜索语料不含 tool_result**（已核验 ClaudeTranscriptHistoryIndex.ts:162 `extractSearchText` 只取 user 与 assistant text blocks）→ 任何投影层截断 tool_result 都不会孤儿化搜索匹配；detail 物化路径（`materializeMessageDetail`，16MiB 上限）确实会构造巨型 ChatMessage → 按派单指示纳入子项 3。
4. **`resolveExactUserMessage` 只解析 user 消息**（rewind/fork 预填输入；ConversationController.ts:966-996，fork 走 Tab.ts:1117 同入口）→ user 消息无 toolCalls，子项 3 不影响 fork/rewind 精确内容解析。
5. **恢复上下文不受截断影响**（已核验 utils/session.ts:88）：`formatToolCallForContext` 对 tool 结果本就只保留 error/blocked 且 500 字符截断。

## 方案设计

### 子项 1：estimateWeight 增量化（store 收口 + per-message 缓存）

把"页面重量计算"从三处重复实现收敛到 `HistoryPageStore` 单点，并按消息对象缓存，使任何调用节奏下 upsert 的成本至多为"新出现消息各算一次"，永不为"全数组反复 stringify"。

- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/history/HistoryPageStore.ts`
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/rendering/HistoryWindowRenderer.ts`
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/controllers/ConversationController.ts`（仅 rewind 内联公式改走 store）
- 测试：`tests/unit/features/chat/history/HistoryPageStore.test.ts`、`tests/unit/features/chat/rendering/HistoryWindowRenderer.test.ts`

**关键签名/数据结构**

```ts
// HistoryPageStoreOptions 增：
messageWeightFn?: (message: ChatMessage) => number;  // 默认 JSON.stringify(m).length * 2；测试注入计数器断言调用次数

// HistoryPageStore 增：
private readonly messageWeights = new WeakMap<ChatMessage, number>();
private computeWeight(messages: ChatMessage[]): number;  // 逐消息查缓存，miss 才算并缓存
invalidateMessageWeights(messages: ChatMessage[]): void; // 作废指定消息的缓存条目

// upsertPage 的 input.projectedWeight 变为可选：省略时 store 用 computeWeight 计算
```

- `beginLivePage`/`freezeLivePage` 不再传 `projectedWeight`（删 HistoryWindowRenderer.estimateWeight 的两处调用）；`freezeLivePage` 先 `invalidateMessageWeights(messages)` 再 upsert——处理已核验的变更点：InputController.ts:543 在 begin 之后原地改写 `userMsg.content = preparedTurn.persistedContent`。
- rewind 合成页（ConversationController.ts:1110 的内联 reduce）删除，改省略权重由 store 计算。`toPageInput` 的 provider 供重路径（`projectedChars*2`）不变。
- 整组替换（分页重挂/rewind 重建）自然退化为一次全量：全部 miss → 每条算一次入缓存——与派单"整体替换退化为全量一次"预期一致。
- 正确性边界：缓存键 = 对象身份。流式期间的原地变更只发生在本 turn 消息上，且 freeze 必 invalidate 重算 → 结算值可信；`replaceMessage`/detail 替换均换新对象 → 天然 miss；WeakMap 随对象 GC。**已知漂移源（复核订正）**：异步子代理 settle/hydration 会在 freeze 之后原地改写已冻结进页的消息（`mergeSubagentToolCallsById` 改 `subagent.toolCalls`、StreamController.ts:1517 改 `subagent.result`），无 invalidate 钩子——缓存重量会低估实际值。fail-soft：`projectedWeight` 只是驱逐/开窗预算启发式（×2 系数本就是近似），偏差最坏影响驱逐时序。子项 3 落地后该漂移源头幅度被钳制（单条 ≤256K），漂移有界。

**测试用例（红→绿）**

1. upsertPage 省略 projectedWeight → store 计算值 = 默认公式值（注入 messageWeightFn 计数器）。
2. 同一批消息对象第二次 upsert → messageWeightFn 调用次数为 0（全缓存命中）。
3. freeze 前 invalidate → 变更后的消息重量反映新内容（计数器按预期重算）。
4. 整组替换（新对象数组）→ 每条恰好计算一次；再 upsert 同引用 → 零次。
5. beginLivePage/freezeLivePage 不再自带重量入参，record.projectedWeight 与旧公式等值（对拍旧断言）。
6. rewind 路径（ConversationController.test.ts 既有用例）合成页重量不回归。

**回归风险面**

- 既有测试对 `projectedWeight` 的字面断言（HistoryPageStore.test.ts、HistoryWindowRenderer.test.ts、HistoryFirstScreenBenchmark.test.ts 可能涉及）需对拍更新；行为语义（32MiB 限额、eviction 顺序）不变。
- 弱引用缓存对"消息被 clone 后再 upsert"的路径（如 Tab.ts deepCloneMessages 产物）只是缓存 miss，多算一次，无正确性影响。
- **诚实边界**：在当前已核验的调用图上（每 turn 2 次 upsert、消息对象每轮新建），子项 1 单独的可测收益主要是删两处重复公式 + 为未来任何调用节奏免疫；冻结时对最终内容仍需一次计算。**overcommit 风暴的根除靠子项 3**（数据本身被钳小后，freeze 权重不再超限，风暴触发条件消失）。子项 1 是成本类别的永久收口，不是本 incident 的独立止血。

### 子项 2：refresh exchange 等待超时（60s，退出等待不插队）

`ProjectionWriteCoordinator.runStored` 增加可选等待超时：只覆盖 FIFO 排队等待，永不打断已获授权的任务体。仅在 `refreshHistorySearchSnapshot` 的交换处接线。

**改动文件**

- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/rendering/ProjectionWriteCoordinator.ts`
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/controllers/ConversationController.ts`
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/history/HistoryDiagnostics.ts`（reason 联合类型加 `'grant_timeout'`）
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/controllers/HistorySearchController.ts`（返回值映射 stale 态）
- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/transcript/ClaudeTranscriptDiagnosticLog.ts`（reason 联合类型成员同步）
- 测试：`tests/unit/features/chat/rendering/ProjectionWriteCoordinator.test.ts`、`tests/unit/features/chat/controllers/ConversationController.test.ts`、`HistorySearchController.test.ts`

**机制**

```ts
runStored<T>(isCancelled: () => boolean, task: () => Promise<T>, options?: { timeoutMs?: number }): Promise<T | null>
// ConversationController:
private static readonly REFRESH_EXCHANGE_GRANT_TIMEOUT_MS = 60_000;
runStoredTransaction<T>(task, options?: { timeoutMs?: number })  // 透传
```

- 入队时挂 timer；timer 到点且 entry 仍未获授权 → 置 entry 的 cancel 闩（复用既有 isCancelled-at-grant-time 跳过机制：队列位保持、pump 到位时跳过不执行）并**立即**向调用方 resolve null（仅靠闩不解封调用方——pump 不会在 holder 释放前运转，必须 race 解封）；获授权则清 timer 正常执行。JS 单线程下 grant 与 timer 回调不交错，settled 标志先到先赢，无竞态。
- **FIFO 不破的论证**：超时方退出等待且不运行任务；它不释放也不夺取任何在跑持有者的授权；后继者的相对顺序不变。"退出等待"不是"插队"。
- 超时后走既有 `exchange === null` 分支：`next.release()` + `reportRefreshNotApplicable`。**判别（复核订正）**：runStored 的 null 无法区分超时/isCancelled/dispose——调用侧在判 'grant_timeout' 前复查事务 staleness（conversation id 或 lease 身份失配）：会话切换取消 → 维持报 'stale'，不得误报 grant_timeout；非 stale 的 null → `'grant_timeout'`（coordinator dispose 边角亦归此标签，teardown 场景仅诊断口径差异，无行为后果）。reason 用新值 `'grant_timeout'`（'stale' 已表示 conversation-switch 失配，混用会污染诊断语义）；reason 类型联合同步实为 **4 处**（复核订正）：HistoryDiagnostics.ts（事件 reason）、ConversationController.ts:709（reportRefreshNotApplicable 参数联合）、HistorySearchController.ts:84（结果 reason）、ClaudeTranscriptDiagnosticLog.ts（落盘 reason）；`mapHistoryDiagnosticEvent` 照抄 reason 字段无需改。
- `HistorySearchController`：**两个调用点**（复核订正——refreshSnapshotAndRerun:226 与 runSearch idle 分支:290 现皆为 resolve 即置 'fresh'）都改为按返回值映射：`not_applicable/grant_timeout` → `snapshotState='stale'`（既有陈旧提示 + Retry 按钮出现），其余 capability 分支维持 'fresh'。**重触发面（复核订正）为 Retry 按钮 / onStreamComplete / 重开面板**——同次 open 内 keystroke 不触发 rebind（:285 守卫只对 'idle' 态 rebind，'stale' 态复用已绑快照）。旧快照全程可搜，无数据损失。
- **60s 依据**：交换临界区本身 <ms（lease 指针交换 + 两次 release + 一条诊断写）；索引 build 在 grant 之外（实测 70ms–16.6s，不占超时预算）；等待纯属队列位（实测病理值 33 分钟）；中止无持久损失且重触发面有三个；60s 处在"索引中"提示的用户耐心边缘，远低于病理等待两个数量级。
- **范围诚实**：只救 search snapshot refresh。`loadOlderWindow`/search-locate 排在卡死 live holder 之后仍会等待（各有既有 deferred 提示），卡死根因（Stop hook 拖长 live turn 不释放 grant）不在本批——超时绝不用于打破 live 持有者。

**测试用例（红→绿）**

1. runStored 带 timeoutMs 排在 live holder 后，timer 到点 → 调用方拿到 null；随后 holder release → 后继者正常获权（无越序、无任务执行）。
2. timer 未到即获授权 → 任务完整执行（超时不打断任务体）。
3. 超时与排队期 isCancelled 并存 → isCancelled 语义优先，均 resolve null。
4. dispose 排空队列时挂起的超时 waiter → resolve null，无泄漏 timer（clearTimeout）。
5. refreshHistorySearchSnapshot：live holder 永不释放 + 60s → 返回 not_applicable/grant_timeout（调用侧复查确认为非 stale）；断言 `next.release()` 被调（lease 释放，可用 spy）；诊断事件 reason=grant_timeout。
6. 判别：超时 null 且会话已切换 → 报 'stale' 而非 grant_timeout；isCancelled 先于 timer 命中 → 同报 'stale'。
7. HistorySearchController 两个调用点（:226/:290）收到 grant_timeout → snapshotState='stale'、Retry 可见；其他 not_applicable 原因仍为 'fresh'（Codex lease-less 行为不回归）。
8. 重触发面：stale 态下同次 open 内 keystroke 不 rebind（:285 守卫只对 'idle'）；Retry / onStreamComplete / 重开面板 → 重新 refresh。

**回归风险面**

- 60s 内 live turn 恰在 61s 完成的边界：刷新中止、搜索结果停在旧快照，直到下一触发面——接受（重触发面充足）。
- reason 联合类型扩展触碰 provider 层诊断类型（ClaudeTranscriptDiagnosticLog），需 typecheck 兜底 exhaustive。
- 超时机制只接线 refresh 一处，其余 runStoredTransaction 调用方行为逐字节不变。

- **顺序约束（不可破坏）**：`extractAgentResult` 内部的 `JSON.parse`/`isStillRunningResult`、`extractDiffData`（走 chunk.toolUseResult 原始对象）、resolvedAnswers 均必须先于钳制拿到全量（钳制在出口，解析在其内）；ChatMessage 只存钳后串。
- **能力路由（不按 provider id，动态判定）**：StreamController 增可选 dep `isClampEnabled?: () => boolean`，默认不钳；写入点每次写入时经该回调求值后调用 helper 钳制。Tab.ts 接线为回调 `() => typeof <当前 service>.acquireHistoryIndex === 'function'`（同 `getHistoryIndexCapableService` 适配口径；service 经 getAgentService 动态取）。**复核订正（中5）**：tab 的 provider 随 conversation.providerId 变，静态 dep 跨 provider 切换后会钳 Codex 持久层——恰是要防的数据丢失；必须每次求值的动态回调。理由：Codex/OpenCode 全量持久化路径（`ChatState.messages = [...conversation.messages]`，Conversation.messages 为持久存储）盲钳会**造成持久层数据丢失**；Claude 侧 ChatMessage 投影为纯视图（transcript 为真相源、原生会话仅存元数据）→ 钳制无损。SubagentManager 的钳制回调共用同一接线。provider-owned 源头（sdkSubagentSidecar/ClaudeHistoryStore）天然 Claude-only，无条件安全。
- **"查看全文"一期不做 UI affordance**：live 消息带本地 id 本就 miss 索引，须等 turn 落盘 + 快照刷新后 detail 管道（loadMessageDetail，16MiB 上限）才可用——marker + `resultTruncated` 元数据先行，B4/A2 复用留二期。
- fork/rewind 精确内容：不受影响（背景节核验 4）；会话恢复上下文：不受影响（核验 5）。

**测试用例（红→绿）**

1. helper：阈值内原样返回；超限返回前缀+marker+originalChars；空串/undefined 边界。
2. handleToolResult 大结果 → 赋值串长度 ≤ 阈值+marker、`resultTruncated.originalChars` 正确；AskUserQuestion 豁免；diff 工具（Write/Edit）的 diffData 路径不受影响（断言 toolUseResult 消费先于钳制）。
3. handleToolOutput 连续追加跨过阈值 → 停在阈值、追加被丢弃、metadata 只置一次。
4. 源头钳制：loadSubagentToolCalls / loadSubagentFinalResult 返回 >256K → 两个消费者（live `mergeSubagentToolCallsById`:1580 / 历史侧 sidecar 注入 ClaudeHistoryStore.ts:168-175）拿到的均为钳后串。
5. extractAgentResult 唯一出口（注入钳制回调）：大输出 → 返回值钳制；内部 JSON.parse/isStillRunningResult 仍用全量输入（断言解析先于钳制）；回调缺省 → 原样返回。
6. applySubagentToTaskToolCall：异步 settle 大结果 → `taskToolCall.result` 与 `taskToolCall.subagent.result` 均为钳后值；**共享对象不被原地改写**（幂等守卫：重复 apply + 一次 hydration merge 后 `mergeToolCallFields` 去重语义不破坏）。
7. 动态门：isClampEnabled 回调在 provider 切换后（service 换为非 index-capable）求值翻转为 false → 后续写入不钳；dep 缺省 → 一律不钳（Codex 行为逐字节不变的守卫用例）。
8. materializeSDKMessages：含 >256K tool_result 的 detail 消息 → 投影钳制 + marker；buildAsyncSubagentInfo 回写同钳；user 消息内容永不触碰；同输入下索引 searchCorpus 不变（语料在索引期生成、与物化钳制正交）。
9. 回归：resolveExactUserMessage 场景（大 user 消息 + 钳后 assistant 结果并存）→ rewind 预填仍取全文 user 内容。

**回归风险面**

- Claude live 路径显示：工具块只显示前 256K + marker——依赖"从 UI 内联读/复制超 256K 工具输出"的工作流受损（缓解：阈值宽裕、marker 标明原文规模、CLI/transcript 仍是全保真视图、二期 detail 加载补 affordance）。
- 历史窗口/详情页同样显示 marker——与渲染侧"超 256K 拒渲"的既有行为一致，无净 UX 损失。
- 共享引用语义：源头钳制方案不触碰 manager 对象身份（写入点 8 的两难已消解）；SubagentManager 钳制回调的注入方式（构造参数/可选 dep）须保证 Codex 路径零变化（守卫用例 5/7），实现期以引用关系与幂等用例（用例 6）覆盖。
- Codex 全量持久化路径必须保持零变化（守卫用例 5 把关）。
- 草稿尾持久化边角：Claude 非原生会话的 draft tail 理论上可含钳后串（实际 draft 尾无 tool result），风险可忽略、记录备查。
- 本子项交付后须独立复核（派单要求）：重点核对写入点清单完整性（漏一处即超重通道残留）与顺序约束。

## 风险与权衡（批次级）

- **顺序取舍（复核订正）**：交付顺序 2→3→1，子项 1 并入子项 3 批次收尾。因果上 3 是 overcommit 风暴的根除项（数据被钳小 → freeze 权重不超限 → 无风暴）；2 最小最快、独立解搜索面板卡死，先行交付；1 非独立止血（见其诚实边界），居首只会延迟真正的止血项，故随 3 的批次一并收尾。三项正交，任一单独部署均无相互依赖。
- **不做的事**：诊断节流（用户已否决；项 3 落地后风暴自然消退——观察项：诊断事件含主线程同步 `appendFileSync`，风暴本身贡献卡顿，消退即可，不改写入机制）；卡死 live holder 的根因（Stop hook 拦截拖长 turn，独立工作线）；"查看全文" UI（二期）。
- **需用户确认的点**：①60s 超时值（可调常量，依据见子项 2）；②256K 阈值（对齐既有渲染常量，依据见子项 3）；③grant_timeout 是否要独立 reason 值（推荐独立；若坚持复用 'stale' 机制亦通、诊断语义受损）。
