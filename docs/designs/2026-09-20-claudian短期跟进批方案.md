# 背景与问题

Claudian 3.0.3 已完成窗口化与四轮热修；本方案对 9 项遗留逐项实证，收敛短期修复边界，重点消除超大 JSONL 行导致的历史静默丢失，并避免为伪问题或中期状态机议题扩大改造。

基线：`14269f5da7b32250f416ebb70ee414dc84aac693`。

## 1. L2：双端有界结构扫描恢复 oversized 身份

### 核实

`/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/ClaudeTranscriptHistoryIndex.ts:446-486` 只读取行首 256 KiB。有效 CC 行若 `message.content` 本身超过 16 MiB，位于 `message` 后的顶层 `uuid`、`timestamp` 不可见；`sdkBranchFilter.ts:99-107,188-194` 依赖 `uuid → parentUuid` 链回溯，链断后更早历史可能在 `:269-274` 被静默过滤。

实机样本补充：当前唯一 >16 MiB 行的巨量字段是尾部 `toolUseResult`，其 `uuid` 位于约 32 KiB，现有前缀扫描可恢复；这不否定 message-content-huge 形状，只说明必须保留前缀扫描，不能改成仅尾扫。

### 推荐方案

采用“前缀结构扫描 + 后缀逆向结构扫描 + 保守合并”，不提高 16 MiB 整行解析上限。

1. 在 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/ClaudeTranscriptHistoryIndex.ts:27-32` 增加独立尾窗常量，建议 `OVERSIZED_FACTS_TAIL_READ_BYTES = 256 * 1024`。理由：与现有前缀预算对称；正常 CC 长尾字段远小于该值。双端最坏读取 512 KiB/超限行，仍有界。不要把窗口做成配置项。
2. 保留 `parseOversizedLineFacts` 作为前向扫描器；新增专用后缀扫描器，从真实行末反向解析 JSON token、字符串转义与 `{}`/`[]` 深度，只接受完整、位于顶层对象深度的 `uuid`、`parentUuid`、`timestamp`、`type`、`sourceToolUseID`。不得用正则或裸 `lastIndexOf('"uuid"')`，避免命中 `message.content`/`toolUseResult` 内文本。
3. `extractOversizedLineFacts`（`:446-457`）分别读取 `[offset, offset+prefix)` 与 `[offset+length-tail, offset+length)`；窗口不重叠时各扫一次，重叠时可直接对完整合并缓冲区复用前向扫描，避免重复解释。
4. 合并规则按字段执行：仅一侧有值则采用；两侧相同则采用；两侧冲突则置为 unknown，记录 conflict，绝不猜测。`toolResultIds` 仍以前缀为主并去重，因为其结构可能位于巨型 `message.content` 内；尾扫只补顶层身份字段。
5. `appendOversizedEntry`（`:459-486`）继续产出同一种 opaque entry；恢复到 `uuid/parentUuid` 后自然接回现有 branch filter、placeholder、turn 归属逻辑，不另造第二类 entry。
6. `finalizeIndex`（`:499-513`）的 fail-closed 规则保留：带 `resumeAtMessageId` 且仍有 opaque entry 缺 `uuid/parentUuid` 时继续拒绝。L2 只扩大“可证明安全”的集合，不弱化分支正确性。
7. worker eval 模板 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/history/ClaudeTranscriptHistoryIndex.ts:828-891` 注入新常量、后缀解析函数、合并函数；顺序须位于 `extractOversizedLineFacts` 序列化前。direct/worker 必须调用同一组函数，禁止维护两套算法。
8. 扩展 `TranscriptLineSkipEvent` 与 `TranscriptIndexDiagnosticEvent`（`:102-106,936-949`）的非敏感字段：
   - `identityRecovery: 'prefix' | 'suffix' | 'both' | 'unresolved' | 'conflict'`
   - `recoveredIdentityFields?: Array<'uuid' | 'parentUuid' | 'type' | 'timestamp'>`
   诊断不记录字段值和行内容。`line_skipped` 即现成通道，无需新增事件类型。

### 备选及权衡

- 扩大前缀至 16 MiB 以上：仍无法覆盖无上界内容，且违背有界退化，否决。
- 流式完整 JSON parser：语义最完整，但新增 parser 状态机与维护面远大于只恢复顶层身份；短期不采用。
- 固定尾窗正则：实现小但可能把用户文本中的伪 key 当事实，否决。

### 测试要点

目标：`/Users/vincentwang/Documents/NoteVault/tools/claudian/tests/unit/providers/claude/history/ClaudeTranscriptHistoryIndex.test.ts:393-553`。

- 构造 `parentUuid,type,message(>maxLineBytes),uuid,timestamp,尾字段` 顺序，断言 suffix 恢复身份、前序 ancestry 保留。
- 保留现有巨大 `toolUseResult`/前缀恢复用例，防止“修 message-content 却回归 toolUseResult”。
- 前后窗重叠、UTF-8 多字节、转义反斜杠/引号、内容内伪 `uuid`、重复顶层 key 冲突、尾窗仍截断等反例。
- direct 与 worker 结果逐字段对拍；worker 不支持环境保留现有 fallback 测试。
- 诊断只含 recovery 枚举与字段名，不含正文/UUID 值。

## 2. L1：resume fatal 与 fork/rewind 按钮

### 核实

1. **会话级 fatal 确实存在**：`ClaudeTranscriptHistoryIndex.ts:499-513` 在带 resume anchor 且任一 opaque 行缺可靠 `uuid/parentUuid` 时返回 failed；`ClaudeConversationHistoryService.ts:298-310` 将其抛出；`ConversationController.ts:246-278` 未降级，最终 `TabManager.ts:404-442` 进入 hydration error。其触发范围是“已带 resume/fork checkpoint 的会话 + 无法证明分支链安全”，不是普通 oversized 会话全部打不开。
2. `MessageRenderer.ts:565-572,598-602` 仅在投影 user message 有 `userMessageId`，且能找到前置 assistant UUID 和后续 response 时渲染 rewind/fork。message-content-huge 的 opaque 行本身 `projectionKind='skip'`，不会形成可操作 user bubble；其他按钮是否可用由各目标现有元数据决定。
3. 点击后二次校验已存在：rewind 在 `ConversationController.ts:910-935`，fork 在 `Tab.ts:1094-1119`；summary 目标还会先做 detail load。故“按钮不预禁用”只会在 detail 不可取时产生一次 Notice，不造成错误操作。

### 裁决

本批不新增目标级 capability 状态，也不改变按钮。理由：

- L2 会修复已知的合法 message-content-huge 形状。
- 剩余 unresolved 行无法安全判断 checkpoint 前缀；将会话级 fail-closed 改为猜测或无分支全量展示，会制造更严重的分支串线。
- 真正的“目标级可操作性”需索引向 UI 输出 checkpoint 可验证性，属于中期双轨/分支能力契约，不应塞进短期按钮条件。

本批仅新增集成断言：合法 suffix-recovered 行的 rewound/forked 会话可 hydrate；结构不可信行仍明确失败；无 UUID 目标不渲染或点击后 Notice 的既有行为不回归。

## 3. F1：rewind 合成页必须声明内存源

### 核实

`ConversationController.ts:974-1008` 创建 `rewind:{start}:{end}` 合成页；`HistoryPageStore.ts:256-279` 可清空任何非 mounted、非 pinned、非 `live:` 页的数据；`ConversationController.ts:339-366` 重物化只接受磁盘 lease 返回完全相同的 `pageKey`，磁盘页为 `w:{snapshotIdentity}:{start}:{end}`，故必返回 null。该页包含 rewind 后的内存真相，旧索引不能作为其重载源。

### 推荐方案

不用 `pageKey.startsWith('rewind:')` 再添隐式特判；扩展页来源语义：

1. `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/history/HistoryPageStore.ts:19-36,67-97`：为记录/输入增加 `retention: 'reloadable' | 'memory-only'`（默认 `reloadable`），`enforceLimits` 不驱逐 `memory-only` 页；超预算沿用 `page_data_overcommit` 明示。
2. `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/rendering/HistoryWindowRenderer.ts:16-18,102-110`：透传 retention。
3. `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/features/chat/controllers/ConversationController.ts:1005-1012`：rewind 合成页标记 `memory-only`；普通 `toPageInput` 仍默认 reloadable。
4. `rematerializeHistoryPage` 对 memory-only 理论上不可达；若被调用，立即返回 null 并记录诊断/断言测试，避免错误读 stale 索引。

选择“内存源豁免”而非“rewind 页降级成磁盘页”：磁盘快照仍含被 rewind 丢弃的分支，按 range 重载会破坏 rewind 语义。当前 `state.messages` 本已持有同一投影，保留页数组不会引入同量级的新内容副本。

### 测试要点

- 极小 `maxPages/maxProjectedWeight` 下 rewind 页 unmount 后 `messages` 仍保留，spacer 可重挂。
- 普通页仍可 evict/rematerialize。
- rewind 后搜索命中合成页无需磁盘 `loadWindow`；旧分支不复现。
- memory-only 导致预算超限时有诊断，不静默突破。

## 4. F2：observer `fromOffset`

### 核实

当前唯一生产传递链为：`ClaudeConversationHistoryService.ts:609-619` 返回 `current.index.committedSize` → `ConversationController.ts:270-273/476-478/729-731` 保存 `historySnapshotOffset` → `Tab.ts:592` 交给 runtime → `ClaudeChatRuntime.ts:2554-2556` → `ClaudeTranscriptTurnObserver.ts:70-77`。

`committedSize` 在 `ClaudeTranscriptHistoryIndex.ts:637-640,669,702,724-729` 只推进到完整换行后一字节；普通半行和 EOF-in-discard 均停在上一完整换行。因此 2.6.1 后 `fromOffset` 已保证是行边界，绕过 recover 是有意避免重复扫描，不是缺陷。

### 裁决与测试

不改生产代码。补跨层契约测试：索引快照以半行结束时 page `snapshotOffset === committedSize`；observer 从该 offset prime，补齐半行及下一行后两行均被消费且不重复旧行。若未来新增非索引来源，`setTranscriptObserverStartOffset` 的参数契约应升级为带品牌/结构的 committed boundary，而不是在 observer 内无条件 recover。

## 5. L4：EOF-in-discard 诊断双计

### 核实与方案

`ClaudeTranscriptHistoryIndex.ts:716-720` 对尚未闭合、尚未形成 opaque entry 的 oversized 半行提前发 `line_skipped`；下一次从 `committedSize` 重建且行闭合后，`:699-701` 再发一次，语义双计。

删除 EOF 分支的 `onLineSkipped` 调用。partial result 已由 `status:'partial'` 和 `partial_snapshot` 诊断表达；`line_skipped` 只代表本次快照内已闭合并被 opaque/malformed 处理的完整行。无需 pending 标记，因为 build 无跨快照持久诊断状态，标记反而引入去重生命周期。

测试：第一次 EOF-in-discard 为 partial 且 0 个 `line_skipped`；追加换行后重建恰好 1 个 oversized 事件；完整 oversized 行仍恰好 1 个。

## 6. F4：分母补刷与保存门禁解耦

### 核实与方案

`TabManager.ts:352-375` 把 passive runtime sync 和 `refreshUsageWindow` 放在同一条件内；`hasPendingConversationSave=true` 时两者都跳过。前者必须保护未保存的本地状态，后者只读 provider settings 并更新内存 usage，见 `ConversationController.ts:1193-1223`，不依赖持久化成功。

重排 `switchToTab` READY 分支：

1. READY、非 streaming、有消息且有 conversation 时总是读取 conversation shell，并调用 `refreshUsageWindow`。
2. 仅 `tab.service && !hasPendingConversationSave` 时执行 `syncConversationState`。
3. 不把 refresh 移到保存重试链；它应由激活事件确定性触发。

测试：pending save=true 时 `syncConversationState` 不调用，但 `refreshUsageWindow` 调用且分母更新；无 conversation/streaming 分支维持现状。需确认 streaming 时是否也应刷新：本方案维持现状，避免流中改 UI 分母；流结束已有 usage 更新。

## 7. F5：search snapshot lease 交换并发

### 核实与方案

`loadOlderWindow` 在 `ConversationController.ts:442-485` 捕获旧 lease 并跨 await 使用；`refreshHistorySearchSnapshot` 在 `:620-645` 新 lease ready 后立即 release previous。release 会撤销全局索引 LRU 保护（`ClaudeConversationHistoryService.ts:264-277`），旧 load 中途可能遇到缓存逐出。虽然 Retry 可恢复，但一次用户动作不应依赖重试。

推荐复用现有 `ProjectionWriteCoordinator`，不新造 lease 引用计数：将 refresh 的“校验当前会话 → acquire next → await ready → state swap → release previous”整体放入 `runStoredTransaction`。`loadOlderWindow` 已在同一 stored transaction 内，二者因而串行；失败回滚逻辑保留。进入 transaction 后及 `await next.ready` 后均检查 stale；stale 时释放 next，不改 state，并按 not-applicable/stale 结果收口。

不推荐只在 `loadOlderWindow` 捕获异常重试：仍有空窗且隐藏竞态；不推荐修改 provider lease 为 retain/release：问题发生在 feature 层的所有权交换，扩大 core/provider 接口没有必要。

测试：用 deferred old `loadWindow` 启动 loadOlder，再触发 refresh；断言 old load 完成前 previous 不 release、next 不成为 active；完成后 swap/release 顺序正确。另测切会话时 next 释放且不复活旧 lease。

## 8. F6：reveal mount 统一 stored 协议

### 核实与方案

`HistoryWindowRenderer.ts:481-485` 对 resident page 直接 `mount`；evicted page 则在 `:514-517` 经 `coordinator.runStored`。流式期间搜索命中 resident-but-unmounted 页，会绕过 DOM 写入协议。当前通常无害，但破坏了“所有 stored DOM 写均经 coordinator”的不变量。

提取一个 `mountIfCurrent(record, capturedContext)` 小路径：无论 resident 还是 rematerialized，最终 mount 均经 `runStored`，并统一检查 disposed/conversation/domEpoch、目标仍需 search/visible/adjacent、record 仍为 pageStore 当前记录。数据 rematerialize 仍在 lease 外执行，避免长时间占用 stored grant。

测试：live lease 持有时 resident 页 reveal 不立即 mount；释放后 mount；期间切会话/DOM epoch 变化则不 mount。保留 evicted dedupe 测试。

## 9. Codex `usage.model` 显式化

### 核实与方案

OpenCode 已在 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/opencode/runtime/OpencodeChatRuntime.ts:370-374,1073-1079` 调 `buildAcpUsageInfo` 时传 model，故 OpenCode 为伪问题。

Codex 的 live notification 路径 `CodexNotificationRouter.ts:440-455` 和 transcript tail 路径 `CodexSessionFileTail.ts:248-256,543-556` 均不设置 model，依赖 `StreamController.ts:386-390` 从活动 selector 回填。该依赖会使绕过 StreamController 的未来 usage 消费路径缺失权威标签。

方案：

1. `CodexChatRuntime.ts:266,354-372,506-510` 计算一次 `resolvedModel = model ?? DEFAULT_CODEX_PRIMARY_MODEL`，同时注入 `CodexNotificationRouter` 和 `CodexFileTailEngine`；后续 RPC 也复用该值，避免同 turn 多次 fallback。
2. `CodexNotificationRouter.ts:440-455` 构造 `UsageInfo` 时写 `model`。
3. `CodexSessionFileTail.ts:543-556,582-587` 让 tail state/builder 持有 model，并在 usage 写入时设置。
4. 保留 StreamController 回填作为 provider-neutral 防御兼容，不删除；新增 provider 必须自行提供 model 的契约在测试中固定。

测试：live notification、transcript tail 两条路径都断言 model；queryOptions 覆盖模型和默认模型各一例；StreamController 已有无 model 回填行为继续通过。

## 项间耦合与实施分批

### 批 A：索引正确性（先做，`implementer-max`）

- L2 双端扫描
- L4 EOF 诊断
- F2 契约测试
- L1 hydration/按钮结论验证测试

原因：共用 oversized fixture、worker/direct 对拍和 committed boundary；先冻结索引语义，后续 UI 批才有可信数据源。L2 与 L4 必须同批，避免诊断测试基线反复变化。

### 批 B：窗口页与 lease 协议（批 A 后，`implementer-max`）

- F1 memory-only 页
- F5 refresh 交换串行化
- F6 reveal mount 统一 stored 协议

原因：三项共享 page store、window renderer、projection coordinator 与 ConversationController；一起测试才能覆盖“内存真相—重物化—DOM 写—索引保护”的完整生命周期。

### 批 C：独立低耦合修正（可与批 B 并行，但合入建议最后，`implementer-high`）

- F4 分母补刷解耦
- Codex usage.model 显式化

二者都触及 usage，但一项是 tab 激活、一项是 provider 事件生产；无需互相等待。合入最后便于单独回归多 provider usage。

每批独立提交、独立跑完整门禁；批 A/B 属高风险，实施后各派 reviewer 复核。批 C 可一次 reviewer 复核。

# 风险与权衡

1. **尾扫正确性优先于恢复率**：无法证明顶层结构时必须 unresolved；不能为了打开会话误接 ancestry。
2. **256 KiB 尾窗是预算，不是格式保证**：双端扫描覆盖当前两类已知形状；若未来同一行同时有超大 message 和超大尾字段，仍会 fail-close。诊断 recovery 字段用于确认是否需要中期流式 parser。
3. **memory-only 页会允许显式 overcommit**：这是正确取舍，因为其磁盘源已失真；当前 `state.messages` 本来也保留该投影。若 rewind 后页面本身过大，后续应设计可重建的“rewind snapshot source”，不应偷读旧索引。
4. **F5 串行化会让 refresh 等待分页完成**：相比索引失去保护更可控；refresh 本来就是搜索前后台动作，不应抢占用户正在进行的分页事务。
5. **L1 中期边界**：目标级预禁用需要公开 checkpoint 可验证性，并统一 fork/rewind capability；建议并入中期双轨对账/状态机方案，不在本批临时加 UI flag。
6. **待用户确认**：
   - 是否接受尾窗固定为 256 KiB，并对“双端都被巨型字段遮挡”的极端形状继续 fail-close。推荐接受。
   - 是否接受 rewind memory-only 页在预算压力下显式 overcommit，而不是从 stale 磁盘重建。推荐接受。
   - F4 是否维持“streaming 时不补刷分母”。推荐维持；本缺陷只针对 pending save。

## 不纳入本批 / 并入中期

- 不做 L1 目标级预禁用和 resume 降级展示；并入中期双轨对账后的 branch/checkpoint capability 设计。
- 不做 F2 生产修复；以契约测试封口。
- 不改 OpenCode usage；其 provider 侧已显式写 model。
- 不引入通用流式 JSON parser、全局 lease retain API 或 rewind 磁盘快照层；当前问题可由现有结构正向解决。
