# Claudian 会话标题改为"按最近内容生成"方案

> 修订记录：v1 为"手动增强 + 可选自动"混合方案（被否：不要手动入口）；v2 为"纯自动、每 10 条、最近 3 条各截 100 字符"（素材策略被否：100 字符太少）；v3 基于 98 个真实会话、3712 条 user 消息的实证分析重写素材策略，本文已整体更新。

## 背景与问题

Claudian（本地 2.0.11，含 6 个手工 patch）的会话标题只在**第一条用户消息**后生成一次，之后永不更新。长对话跑题后标题不反映实际内容。目标：每累积 10 条 user 消息自动基于会话内容重新生成标题，素材要足以准确概括"最近在做什么"。

## 实证分析（98 会话 / 3712 条 user 消息，2026-08-09）

数据源：`~/.claude/projects/-Users-vincentwang-Documents-NoteVault/*.jsonl`（SDK transcript）+ `.claudian/sessions/*.meta.json`。分析脚本 `/tmp/claudian_title_analysis.py`。

**会话规模**：user 消息数 p50=7、p75=25、p90=92、max=608。**≥10 条的会话 42 个（43%）**——自动刷新的目标群体不小；50+ 条的重度连续工作流 16 个。

**user 消息长度分布**（字符）：p50=42、p75=123、p90=479、p95=2822、p99=16878、max=446k（贴文件）。

- **71.4% 的消息 ≤100 字符**——典型消息极短（"继续"、"好的"、"进度如何"）
- 总字符量的 90%+ 集中在 8% 的长消息（计划/方案/报错/贴代码）——信息密度两极分化

**关键发现 1：v2"最近 3 条"策略在 26% 的长会话里失效**。≥10 条会话中，11/42（26%）的最近 3 条全是 <40 字符短指令——素材全是"继续/好的"，生成不出有意义的标题。**问题不是"截 100 太短"，是选料本身选到了零信息消息**。

**关键发现 2：每个长会话都有足够的高信息量消息可选**。以"≥40 字符且非噪声"计，≥10 条会话 p25=p50=5 条，取不到 1 条的为 0。

**关键发现 3：11.2% 的 user 消息是噪声**，必须过滤：`This session is being continued...`（compact 续接）、`[Request interrupted by user...`、`<command-*`、`Caveat:`。

**关键发现 4：首条消息是重要素材**（39% 的首条 ≥100 字符，多为带 @路径的任务定义），但 61% 首条也很短，单靠首条也不够。

**话题漂移形态**（抽查 8 个 ≥100 条会话）：绝大多数是**同项目连续工作流**——首条定义项目/任务主线（"@tools/model_proxy/ 代码审查+测试方案"），后续是子题演进与短确认；真正的跨题漂移少。608 条会话从"Delta 调仓优化"到末条"文档更新过了么"，主线未变。**结论：标题要概括的是"任务主线 + 当前子题"，多数刷新周期内正确行为是"标题不变"**——这支撑保留"现标题增量判断"机制。

## 方案设计（v3）

触发机制不变：**每 10 条 user 消息在该轮结束时静默刷新**（hook @80284、`userCount % 10` 无状态取模、status ∈ {success, failed} 门槛、手动 rename 清 status 的不变量）——实证未推翻取模：42/98 会话会触发，608 条会话全程刷 60 次 × <$0.001 ≈ $0.06，成本无约束。素材策略变化不影响触发设计。

### 素材策略：首条 + 高信息量最近消息 + 现标题（增量判断）

在 `regenerateTitle` 内从 `fullConv.messages` 选料：

```text
Current title: "<现标题>"
Return it unchanged if it still accurately summarizes the conversation below.

First request:
<首条 user 消息，截 300>

Recent messages:
- <最近 5 条高信息量 user 消息（≥40字符、非噪声），各截 250，从新到旧>
```

选料规则：

1. **噪声过滤**：跳过以 `This session is being continued` / `[Request interrupted by user` / `<command-` / `<local-command-caveat>` 开头的消息（实证占 11.2%；Caveat 真实形态为 `<local-command-caveat>Caveat:...`）
2. **首条**：任务主线定义，截 300
3. **高信息量最近消息**：`displayContent || content`，过滤噪声后取 **≥40 字符**的最近 5 条，各截 250；若一条都取不到（实证中长会话不存在此情况，兜底给短会话），回退为最近 3 条原始消息各截 100
4. **现标题前缀**：模型判断"仍准确则原样返回"（v2 的模型内抑制，实证支持——同题工作流是主导形态）
5. 素材总长控制在 ~1600 字符

**不纳入 assistant 消息**：实证显示标题概括对象是"用户推进的任务主线"，首条+高信息量 user 指令已覆盖；assistant content 是 contentBlocks 复合结构，提取逻辑显著增加 patch 侵入度，收益不明确。

### 预算：500 截断不是硬约束，patch 放大到 2000

核实：截断点在 service 内部 @57885 `const truncatedUser = this.truncateText(userMessage, 500)`，`truncateText` 仅被 `generateTitle` 调用（@57930 定义、单调用点），放大无副作用。patch `500 → 2000` 一行。首条触发场景输入本 <500，不受影响。（@57846 `buildTitleGenerationPrompt` 的 500 截断是 codex/opencode 的 QueryBacked 路径，claude provider 不经过，不动。）

### patch 点（函数级定位，总计约 56 行，单备份 `main.js.bak-before-title-refresh-patch`）

1. **service 截断放大** @57885：`truncateText(userMessage, 500)` → `2000`（1 行）
2. **service prompt 文案通用化** @57886-57891：`"User's request:"` → `"Conversation excerpt:"`（1 行；素材自带 First request/Recent messages 小标题，多段语义才成立；首条单段场景同样通顺）
3. **system prompt 弱动词禁令** @57842 后 +1 行：`Forbidden weak verbs: "Continue", "Work on", "Handle", "Follow up" — name the concrete task instead`——抑制模型在增量判断时用模糊动词刷新标题
4. **`regenerateTitle` 改造** @77528-77559（~35 行）：加 `{silent}` 参数；素材改为上述"首条+高信息量最近 5 条+现标题前缀"选料逻辑（含噪声过滤、≥40 字符过滤、兜底回退、总长截 1600）；silent 分支（不置 pending/失败静默/成功才 rename+刷 UI）
5. **手动 rename 补不变量** @77426 `finishRename` 内 +1 行：`updateConversation(convId, {titleGenerationStatus: void 0})`——漏改则手改标题在下个 10 条边界被覆盖
6. **hook + `maybeAutoRefreshTitle`** @80284 后（~15 行）：门槛 `enableAutoTitleGeneration && convId && userCount>0 && userCount%10===0 && conv.titleGenerationStatus ∈ {success, failed}`，通过则 `regenerateTitle(convId, {silent: true})`。userCount 判据为 `m.role === "user" && m.content`（content 即 textContent）：tool_result-only 消息 textContent 为空被排除（实测 4270 条 tool_result 消息均有顶层 toolUseResult，已被 isSystemInjectedMessage 过滤，此为兜底）；不用 displayContent——纯文本历史消息 displayContent 为 null 会误杀真实指令

### 准确性与成本权衡

- 单次生成：素材 ~1600 字符（中英混合 ≈ 600-800 tokens）+ system prompt ~120 → ~900 in / 15 out，Haiku 4.5 单次 ≈ **$0.001**。50 条会话全程 5 次 <¥0.05。**成本不构成约束，约束在 patch 侵入度**：v3 比 v2 多 2 处 service 小 patch + 选料逻辑从 6 行涨到 ~30 行，总 patch ~35 → ~55 行，仍在本地先例颗粒度内
- 准确性收益相对 v2：覆盖 26%"最近全是短指令"的失效会话；首条保留任务主线避免"标题只反映琐碎子题"；现标题增量判断避免同题工作流里的措辞漂移

### 失败静默

同 v2：silent 路径失败不写 status、不刷 UI、无 Notice，下一边界自然重试。

### 实施方式：bundle patch（前提不变）

按 [[2026-08-09-claudian升级价值评估]]（confirmed）：留守 2.0.11（未压缩可 patch），上游 ≥2.0.36 minify 后 bundle patch 不可行；fork 源码成本不成比例。本 patch ~55 行，同本地 6 个先例颗粒度。

## 风险与权衡

1. bundle patch 固有脆弱性：升级即丢——既定前提
2. **patch 点 4 漏改 → 覆盖用户手改标题**：实施与验证单列
3. 高信息量阈值 40 字符、各截 250/300、预算 1600/2000 均为经验值：实证分布支持（p75=123、p90=479），但非精调；实施后可按实际生成质量微调字面量
4. compact 续接会话的首条可能是 "This session is being continued"（噪声）——此时"首条"素材为空，仅靠最近高信息量消息，标题仍准确但可能丢失最原始主线；接受（compact 后本就进入新阶段）
5. 取模 save 重入重复触发：abort 互斥兜底，可接受
6. 模型内抑制的保守倾向：话题已变但滞后一个周期——接受（滞后 < 抖动）

## 验证方式

1. 重载插件（命令面板 Reload app without saving）
2. 新会话聊到第 10 条 user 消息 → 标题静默更新（无 spinner/Notice）；继续到 20 条再演进
3. **短指令场景**（v2 失效场景）：连续发"继续/好的/嗯"类短消息穿插任务指令 → 第 10 条时标题应基于最近的任务性指令而非"好的"
4. 同题工作流：话题不变 → 标题保持原字符串（模型原样返回）
5. 手动 rename → 下个 10 条边界不被覆盖
6. compact 续接后的会话 → 噪声消息不进素材，标题不变成 "This session is being continued..."
7. 断网使自动刷新失败 → 无 UI 痕迹，status 保持
8. 回归：首条即时生成行为不变（输入 <500 不受截断放大影响）；failed 按钮手动刷新行为不变
9. 回滚：`cp main.js.bak-before-title-auto-refresh-patch main.js`
