# Claudian 阶段 2 空闲期管道回喂实施设计 v4（已替代）

> 已被 [[2026-08-23-Claudian阶段2-S4S5重设计-v2]] 替代。S1-S3 已实施部署（有效）；S4/S5 实施（61f7692）失败回滚；§6 通知时序等前提被 0823 事故证伪。本文档仅作历史参考，S4 待办清单已由 v2 重设计吸收。

## 背景与问题

v3 的 turn lease、feature 仲裁、turn-scoped 状态及 domain/DOM 解耦方向不变；v4 只封闭三项剩余时序缺口，并补全强制关闭与 MessageChannel 错误路径，作为实施终稿。

## 方案设计

### 1. v3 → v4 变更点

| 项目 | v4 定案 |
|---|---|
| turnId 两层不统一 | **选择 InputController 生成 turnId，并随 `ChatTurnRequest → PreparedChatTurn → query()` 传入 runtime。** 理由：只增加一个 provider-neutral 字段，不新增同步 runtime 预留 API，也不改变现有 `prepareTurn()` 调用节奏，侵入最小。runtime 禁止另生成 user turnId。 |
| `completeTurn()` 提前 dequeue | 固定采用复核给出的顺序，不增加“只释放不投递”模式：**清理/finish 旧 feature lease → 执行 deferred restart → settle runtime → `completeTurn()` 放行 dequeue → 触发 feature queuedMessage**。取消路径相同，feature cancellation 必须先于 channel 放行。 |
| ownership 转交不完整 | plugin 级最小状态机：`owner + FIFO waiters`；release 后 grant 下一 tab，新 owner必须先 hydrate 最新 conversation、初始化唯一 runtime，再处理 queuedMessage。mirror runtime关闭。 |
| 强制 close 的最终 snapshot | release ownership 前 drain；超时的已入队最终 snapshot持独立 commit token，不再依赖 owner 校验，允许转移后完成一次提交。 |
| MessageChannel 错误路径 | `beginExternalTurn`、user dequeue、`completeTurn` 发现占用不一致时，调用 runtime 的协议错误处理，结算对应 turn/waiters并记录诊断；不得让异常冒泡杀死 consumer 总循环。 |

除本节及下述增量外，v3 以下内容原样沿用：§2 RuntimeTurn 对象化、§3 InputController 内 feature 排他仲裁、§5 StreamController/SubagentManager 与 DOM 解耦、§6 完整保存快照字段与 save call-site 迁移表、§7 有界完成协议、§8 分步落地及测试主体。

### 2. user turnId 单一来源

#### 2.1 数据契约

修改 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/core/runtime/types.ts`：

```typescript
interface ChatTurnRequest {
  turnId: string;
  // 其余字段不变
}

interface PreparedChatTurn {
  turnId: string;
  request: ChatTurnRequest;
  // 其余字段不变
}
```

规则：

1. `/src/features/chat/controllers/InputController.ts:sendMessage()` 在取得 conversation writer ownership、准备创建 feature lease 前，用现有 ID 生成器生成唯一 `turnId`。
2. 同一个 turnId 依次写入 `ChatTurnRequest.turnId`、`PreparedChatTurn.turnId`、`activeFeatureTurn.turnId`。
3. Claude `/src/providers/claude/prompt/ClaudeTurnEncoder.ts:encodeClaudeTurn()` 原样复制 turnId；Codex/OpenCode encoder 同样透传，不解释其语义。
4. `/src/providers/claude/runtime/ClaudeChatRuntime.ts:query()` 与 `queryViaPersistent()` 必须使用 `PreparedChatTurn.turnId` 创建 user `RuntimeTurn`；禁止 fallback 生成另一个 ID。重复或空 turnId 是协议错误，返回 error chunk并结算 generator。
5. auto turnId 仍由 Claude runtime 在 `ensureAutoTurn()` 中生成；该 ID通过同步 `onAutoTurnStarted` 传给 feature，feature直接采用，不二次生成。

#### 2.2 完成归属

feature lease、RuntimeTurn、MessageChannel queue item、canonical merged waiters、cancel API、日志字段统一使用同一个 turnId。任何完成/取消回调都同时校验：

```text
turnId 相同
runtime generation 相同
feature generation 相同
conversationId 相同
writer owner tabId 相同
```

任一不符只清来件所属旧 turn，不改当前 turn。

### 3. 完成与取消的固定顺序

#### 3.1 正常完成

`SDK result` 后按以下不可调整顺序执行：

```text
1. RuntimeTurn.phase = projecting
2. await feature project/finalize
3. feature finishFeatureTurn(turnId)
   - finalize text/thinking/tool state
   - 清旧 turn 的 currentContentEl/currentText/currentThinking
   - state.isStreaming = false
   - 不调用 processQueuedMessage()
4. await executeDeferredRestartIfAny()
   - 旧 Query 此时已无 collecting/projecting turn
5. settleRuntimeTurn(turnId)
   - phase = settled
   - 结算并清全部 waiters
   - 删除 turn-scoped state
6. messageChannel.completeTurn(turnId)
   - 清 activeTurnId
   - 才允许 async iterator dequeue 下一 SDK user message
7. onTurnReleased(turnId)
   - feature 校验无 active lease
   - writer tab 调 processQueuedMessage()
```

`finishFeatureTurn()` 与 `processQueuedMessage()` 必须拆开，禁止 finish 内部自动发送下一轮。

#### 3.2 取消与协议错误

取消同样先清 feature、后放 channel：

```text
abort/generation++
→ await onAutoTurnCancelled / cancelTurnProjection
→ 执行或丢弃 deferred restart（按取消原因）
→ settle waiters（onDone 或 onError）
→ 删除 RuntimeTurn
→ completeTurn(active turnId)
→ onTurnReleased / processQueuedMessage
```

- session switch、reset、tab destroy、plugin cleanup：取消旧 feature lease，丢弃 deferred config restart，结算所有 queued turns；不触发旧 tab的 queuedMessage。
- 普通用户 cancel：取消 active turn，保留 UI queuedMessage按现有“恢复到输入框”语义；不自动发送。
- runtime 协议错误：以 `onError(new Error(...))` 结算相关 waiter，记录 turnId、expected activeTurnId、phase；consumer 捕获并继续下一 SDK message。

#### 3.3 MessageChannel 错误恢复

`ClaudeMessageChannel` 方法返回 discriminated result，不直接抛占用异常：

```typescript
type TurnChannelResult =
  | { ok: true }
  | { ok: false; code: 'active_turn_exists' | 'turn_mismatch' | 'unknown_turn'; activeTurnId: string | null };
```

- `beginExternalTurn(turnId)` 失败：runtime cancel 新建 auto turn；若已有 active turn，将消息按已有 turn处理，不能创建第二 lease。
- user dequeue 与 runtime queued turn不匹配：取消该 queue item对应 turn及 waiters，记录诊断，继续取下一 item。
- `completeTurn(turnId)` mismatch：先由 runtime cancel 被报告的实际 active turn，再重试一次正确 release；仍失败则关闭该 channel并结算其全部 turns，但 consumer 外层继续由 runtime决定是否重建 Query。

### 4. conversation 单写者 ownership 状态机

#### 4.1 归属与作用域

状态必须位于 `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/main.ts` 的 `ClaudianPlugin` 实例，不能位于单个 `TabManager`，确保多个 view 共用：

```typescript
interface ConversationWriterState {
  ownerTabId: string | null;
  waiters: Array<{
    tabId: string;
    wake: (granted: boolean) => void;
  }>;
  saveTail: Promise<void>;
  pendingFinalCommit?: FinalCommitToken;
}

private conversationWriters: Map<string, ConversationWriterState>;
```

waiters 为 FIFO 数组；同 tabId最多一个 waiter，重复 request 返回同一等待 Promise。

#### 4.2 状态机

```text
requestOwnership(conversationId, tabId)
  ├─ owner=null → owner=tabId → grant(tabId)
  ├─ owner=tabId → 立即成功
  └─ 其他 owner → 去重后 push FIFO waiter；tab保持 mirror/read-only

releaseOwnership(conversationId, ownerTabId)
  ├─ 校验调用者是 owner
  ├─ 等待 saveTail drain；强制 close按 §4.5
  ├─ 关闭/解绑 owner runtime
  ├─ owner=null
  └─ shift FIFO next → owner=next.tabId → grant(next)

grant(tabId)
  → await hydrate latest conversation from plugin storage
  → 覆盖该 tab 的 messages/usage/provider state/session metadata
  → 关闭该 conversation 在其他 mirror tab 的 persistent runtime
  → initialize/activate 此 writer tab 的唯一 provider runtime
  → wake(true)
  → InputController.processQueuedMessage()
```

#### 4.3 谁触发 release

- writer tab `switchTo/createNew/closeTab/destroyTab`：操作流程显式调用 release。
- plugin/view destroy：按 conversation 去重，由 owner执行 drain + release；waiters以 `wake(false)` 取消。
- **writer idle 自动转交**：`finishFeatureTurn()` 后，若 `state.isStreaming=false`、runtime 无 active/queued SDK turn、writer 自身无 `queuedMessage`、saveTail 已 drain，且 FIFO waiters非空，则 `InputController` 调 `releaseOwnership()`。这是等待 tab 获得写权的正常推进器。
- writer仍有自身 queuedMessage 时不 release，先处理自身队列；完成后再评估。

#### 4.4 新 owner 激活前置条件

新 owner 绝不能直接消费旧 UI 内存：

1. 从 plugin storage重新 `getConversationById()`；
2. `ConversationController.restoreConversation()` 覆盖 messages、usage、session/providerState、note、external paths、MCP、resume checkpoint；
3. `ensureServiceForConversation()` 只为新 owner创建/绑定 runtime；
4. 确认同 conversation 其他 tab 的 runtime `cleanup/resetSession` 完成；
5. 才调用 `processQueuedMessage()`。

`TabManager.restoreState/openConversation/ensureProviderTabRuntimeReady` 增加 writer 判断：mirror 只 hydrate UI，不启动 persistent runtime。

#### 4.5 强制 close 与最终 snapshot

正常 release 必须先 drain saveTail。强制 close允许最多等待3s：

- 最终 snapshot 入队时签发 `FinalCommitToken {conversationId, commitId, snapshot}`。
- token 一旦入队即脱离 owner 生存期；提交校验 commitId 是否仍为该 conversation 最新最终提交，不再校验 ownerTabId。
- ownership 可在3s超时后转移；旧 final token仍可完成一次提交。
- 新 owner grant 必须等待该 pendingFinalCommit settle，或到同一3s上限后再 hydrate；若超时，读取 storage并以新 snapshot覆盖，旧 token提交前发现 commitId过期则丢弃。

因此不会因 owner已转移而丢弃已排队最终 snapshot，也不会让晚到旧提交覆盖新 owner。

#### 4.6 mirror 与 auto notification

- mirror tab persistent runtime必须关闭；正常情况下不会收到 SDK 通知。
- ownership 切换竞态中，旧 runtime可能已取到 auto notification。此时 runtime仍需完整 drain该 SDK turn、执行阶段 1 notification handler的幂等销账并 `completeTurn`，但 feature callback检查 owner失败后使用 no-op projection：不写 ChatState、不更新 usage、不 save、不创建 DOM。
- 新 owner hydrate transcript/持久化 SubagentInfo后取得最终投影；不得把旧 mirror 的 auto chunks转交给新 runtime，避免伪造跨 Query续流。

### 5. 保存语义增量

v3 §6.2 完整 `ConversationSaveSnapshot` 字段及 §6.4 call-site 表不变，增加：

- snapshot 增加 `commitId`、`writerEpoch`、`isFinal`。
- 普通 snapshot执行前校验当前 owner与 writerEpoch；final token按 §4.5校验 commitId。
- `sessionInvalidationEpoch` 仍采用 `get/ack`，仅成功提交包含该 epoch 的 snapshot后 ack；被合并、取消、超时或 owner转移的普通 snapshot不消费。
- title/status 专用 patch不参与 writer ownership，但必须基于最新 storage对象做字段 patch，不能提交旧 conversation 全对象。

### 6. 阶段 1 通知与回喂边界

保持不变，但严格时序改为：

```text
ensureAutoTurn()
→ messageChannel.beginExternalTurn(turnId)
→ 同步 onAutoTurnStarted（feature取得排他权或明确 no-op mirror）
→ dispatchTaskNotification()
→ return（早退于 transform）
```

TaskOutput 后续 chunks仍走 StreamController/SubagentManager 投影兜底；通知与工具结果均幂等，同一任务只发生一次终态 transition。

## 风险与权衡

- writer 等待会限制同 conversation 多 tab并行输入；这是防止快照分叉覆盖的必要约束。
- config restart 最迟延后一个 turn；不再承诺 Query 重建后续出旧流。
- 强制 close 的 final token让保存可越过 owner生命周期，但只允许最新 commitId提交，避免旧写覆盖。
- channel 协议错误选择局部结算而非击穿 consumer，可能丢一个异常 turn；诊断日志与 transcript hydration负责恢复，不以死锁换完整性。

迁移代价与 v3 相同，不新增组件文件。

## 验证方式

沿用 v3 全部测试，并新增/收紧以下断言：

1. **turnId 贯通**：InputController生成 ID；PreparedChatTurn、RuntimeTurn、MessageChannel item、feature lease完全相同；runtime不另生成 user ID。
2. **完成顺序 spy**：`finishFeatureTurn → deferredRestart → settleRuntimeTurn → completeTurn → processQueuedMessage` 严格有序；取消路径同序。
3. **external turn**：`beginExternalTurn` 与 user dequeue互斥；auto完成后才交付 queued user。
4. **协议错误不杀 consumer**：begin/dequeue/complete三类 mismatch均结算目标 waiter、记录诊断，后续合法 turn仍可处理。
5. **ownership FIFO**：A owner，B/C wait；A idle+save drain后B hydrate/activate/send，再到C。
6. **唯一 runtime**：同 conversation多 tab只有 owner `persistentQuery != null`；grant前旧 owner runtime已关闭。
7. **mirror notification**：旧 mirror竞态收到通知时仅 drain/销账，不写消息、usage、DOM或save。
8. **final snapshot**：force close 3s超时后 ownership转移，旧 final token仍提交；新 commit产生后旧 token失效且不能覆盖。
9. **grant hydrate**：新 owner处理 queuedMessage前，messages、usage、provider/session state、note、external paths、MCP、resume均来自最新 storage。
10. **自动 release条件**：writer有 active turn、自身 queuedMessage或未 drain save时均不转交；三者清空后自动grant FIFO首项。

命令沿用 v3，并增加覆盖 plugin/TabManager ownership 的测试文件。运行时重点复测两个 view打开同一 conversation、writer关闭时慢保存、auto通知与 ownership切换竞态。
