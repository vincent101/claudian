# Claudian 阶段 2 空闲期管道回喂实施设计

> 已被 [[2026-08-22-Claudian阶段2空闲期管道回喂实施设计-v2]] 替代。v1 未覆盖 dequeue 时 turn lease、feature 层排他仲裁、turn-scoped 状态、生命周期取消与 SubagentManager/DOM 解耦，不得用于实施。

## 背景与问题

阶段 1 已用 task-notification 作为异步任务终态权威销账信号；阶段 2 要补齐无 `responseHandler` 轮次的通用 chunk 消费，使自动唤醒轮与 Stop hook block 续轮复用活跃期处理链，完整处理工具活动、UI 与 usage，且不重复销账或渲染。

## 方案设计

### 1. 现状管道

#### 1.1 活跃期：用户消息轮

```text
InputController.sendMessage
  ├─ 创建 userMsg / 空 assistantMsg，写 ChatState
  ├─ activateStreamingAssistantMessage：创建 assistant DOM，并设置 ChatState.currentContentEl
  └─ for await ChatRuntime.query(...)
       └─ ClaudeChatRuntime.queryViaPersistent
            ├─ createResponseHandler + registerResponseHandler
            ├─ MessageChannel.enqueue(user message)
            └─ SDK persistentQuery consumer
                 └─ ClaudeChatRuntime.routeMessage
                      ├─ dispatchTaskNotification：命中即权威销账并早退
                      ├─ transformSDKMessage(SDKMessage → StreamChunk[])
                      ├─ text/thinking 去重、usage 两阶段合并
                      └─ handler.onChunk
                           └─ query generator yield
                                └─ InputController
                                     └─ StreamController.handleStreamChunk(chunk, assistantMsg)
                                          ├─ text/thinking → DOM + ChatMessage.content/contentBlocks
                                          ├─ tool_use/tool_result → ToolCall/UI
                                          ├─ Task tool_result → SubagentManager.handleTaskToolResult
                                          ├─ TaskOutput tool_use/result → SubagentManager.handleAgentOutputToolUse/Result
                                          └─ usage → ChatState.usage → ContextUsageMeter
```

轮终止：SDK `result` 由 `isTurnCompleteMessage()` 识别；`routeMessage()` 调 `MessageChannel.onTurnComplete()` 与 `handler.onDone()`；generator 末尾补 `done`；`InputController.finally` 完成 text/thinking、流状态、SubagentManager 流内状态与 conversation save。

- `/Users/vincentwang/Documents/NoteVault/tools/claudian/src/providers/claude/runtime/ClaudeChatRuntime.ts`：`startResponseConsumer()`、`routeMessage()`、`query()`、`queryViaPersistent()`。

#### 1.2 空闲期：自动唤醒轮与 Stop hook block 续轮

两类轮次都没有 `query()` 创建的 `responseHandler`，现行路径相同：

```text
SDK persistentQuery consumer
  └─ ClaudeChatRuntime.routeMessage
       ├─ task-notification → dispatchTaskNotification 后早退（阶段 1）
       ├─ 其余消息 → transformSDKMessage
       ├─ 无 handler：所有 StreamChunk push 到 _autoTurnBuffer
       └─ SDK result：复制 buffer + consumeTurnMetadata + 清 buffer
            └─ _autoTurnCallback
                 └─ Tab.renderAutoTriggeredTurn
                      ├─ 仅拼 text
                      ├─ tool-only 时造 “(background task completed)”
                      └─ ChatState.addMessage + MessageRenderer.renderStoredMessage
```

当前各 chunk 去向：

| chunk | 活跃期 | 空闲期现状 |
|---|---|---|
| `text` / `thinking` | StreamController 增量渲染并写 `contentBlocks` | buffer；仅 `text` 被最终消费，`thinking` 丢弃 |
| `tool_use` / `tool_result` | StreamController → Tool UI、SubagentManager | buffer；仅用于判断“有工具活动”，实际语义丢弃 |
| `subagent_tool_use/result` | StreamController → 同步子 agent | buffer 后丢弃 |
| `tool_output` | 更新工具输出 DOM/状态 | buffer 后丢弃 |
| `notice` / `error` / `context_compacted` | 对应 UI 与消息状态 | buffer 后丢弃 |
| `usage` | `ChatState.usage` + meter | buffer 后丢弃 |
| `session_init` / `context_window` | runtime 内消费；后者修正 buffered usage | runtime 内消费；修正后的 usage 仍只入 buffer |

`_autoTurnBuffer` 仅在 SDK `result` flush；关闭/重启 persistent query 时直接清空。消费方唯一为 `/src/features/chat/tabs/Tab.ts:renderAutoTriggeredTurn()`。

### 2. 推荐：保留 turn buffer，flush 后复用 StreamController

不新建“等价空闲管线”。等价实现会复制 Task/TaskOutput、工具渲染、usage 过滤、文本 finalization 等规则并再次漂移。空闲期应在 feature 层建立一个临时 assistant turn，然后把原始 `StreamChunk[]` 按序送入现有 `StreamController.handleStreamChunk()`。

保留 buffer，不改成逐 chunk 直通，原因：

1. 空闲期 UI 当前不进入 streaming 生命周期；逐 chunk 直通会引入跨用户轮的共享 DOM 状态竞争。
2. SDK `result` 是既有、可靠的 turn 边界；批量 flush 可在放行 MessageChannel 前原子完成 UI/状态归并。
3. 文本与工具的原始顺序仍由数组保存，交给 StreamController 顺序消费即可。

#### 2.1 明确 turn 归属，禁止按“当前是否有 handler”逐消息判断

在 `ClaudeChatRuntime` 增加 provider 内部状态（名称可按现有命名调整）：

```text
currentTurnSink = null | { kind: 'handler', handlerId } | { kind: 'auto' }
```

规则：

- 某轮第一条属于该轮的消息到达时锁定 sink；有当前 handler 则锁定该 handler，否则锁定 auto。
- 空闲收到阶段 1 的 task-notification 时，通知仍先销账并早退，但若尚无 turn sink，要同时把即将发生的轮锁定为 `auto`；不得把通知本身变成 StreamChunk。
- 后续该轮所有消息都投递到锁定 sink，不因用户此时点击发送、`responseHandlers` 数组发生变化而改道。
- SDK `result` 是唯一正常 turn 结束边界：先完成对应 sink 的 flush/done，再清 `currentTurnSink`，最后允许 MessageChannel 进入下一轮。
- close/restart/error 时清 sink、buffer 与去重标志；若锁定 handler，沿用现有 handler error/done 退出机制。

此项修正一个现存竞态：空闲轮已开始后用户发送消息，会先注册新 handler；若每条消息重新读取“最后一个 handler”，空闲轮的尾部和 `result` 会误投给新用户轮。

#### 2.2 AutoTurn callback 改为可等待

将 `AutoTurnResult` 数据结构保持不变；仅把回调契约改为 `void | Promise<void>`，`routeMessage()` 在 auto turn 的 `result` 分支 `await` 回调。这样临时消息的 chunk 消费、finalize 和保存结束前，不调用该轮的 `MessageChannel.onTurnComplete()`。

空 callback 仍合法；回调异常维持现有 Notice，但必须在 `finally` 中清 buffer、去重状态、metadata 与 turn sink，不能污染下一轮。

#### 2.3 feature 层新增唯一入口

在 `InputController` 新增公开异步方法 `handleAutoTriggeredTurn(result: AutoTurnResult): Promise<void>`，复用其已有 assistant 消息生命周期私有方法；删除 `Tab.ts` 中只拼文本的 `renderAutoTriggeredTurn()`。

处理顺序固定：

1. 若 tab DOM 已脱离，跳过 UI，但仍要处理 `usage` 与 SubagentManager 相关 chunk；不得像现状直接 return 丢状态。DOM 是否存在只控制渲染，不控制业务消费。
2. `subagentManager.resetSpawnedCount()`，把 usage 过滤口径限定到本次 auto turn，避免继承前一用户轮的 `_spawnedThisStream > 0` 导致 usage 被跳过。
3. 创建一个空 `ChatMessage(role='assistant', toolCalls=[], contentBlocks=[])`；优先使用 `metadata.assistantMessageId` 作为 `id`/`assistantMessageId`，否则用现有 ID 生成器。
4. DOM 已连接时，调用现有 `activateStreamingAssistantMessage()` 建立 `currentContentEl`；不调用 `renderStoredMessage()`。
5. 按数组顺序逐个 `await streamController.handleStreamChunk(chunk, assistantMsg)`。因此 Task、TaskOutput、普通工具、thinking、notice、error、compact、usage 全部走活跃期逻辑。
6. 调 `flush/finalize`：`hideThinkingIndicator()`、`finalizeCurrentThinkingBlock(assistantMsg)`、`finalizeCurrentTextBlock(assistantMsg)`、`subagentManager.resetStreamingState()`，然后清 `currentContentEl/currentText* / currentThinkingState` 与 `activeStreamingAssistantMessage`。
7. 判断消息是否有可持久化可见内容：非空 text、可见 tool call/content block、thinking、notice/error/compact 任一存在则保留；仅含隐藏 `TaskOutput` 或纯 usage 时，移除临时空 message 与空 DOM。不得生成 `“(background task completed)”` 占位文本。
8. 无论是否保留消息，usage 与 SubagentManager 状态更新都已生效。

`setupServiceCallbacks()` 注册 async callback：

```text
await inputController.handleAutoTriggeredTurn(result)
await conversationController.save(true)
```

保存失败沿用 background best-effort 策略记录 Notice/日志，不回滚已完成的状态投影。

### 3. 防重复渲染

现状重复风险来自三处，按职责分别处理。

#### 3.1 禁止“流式处理后再 stored render”

`StreamController.handleStreamChunk()` 已实时创建/更新 DOM，并把数据写入同一个 `ChatMessage`。处理完后若再调用 `MessageRenderer.renderStoredMessage()`，text、tool、thinking 会各出现第二份。新入口只能：

```text
renderer.addMessage(empty assistant) → StreamController 逐 chunk → finalize
```

不能再调用 `renderStoredMessage(assistantMsg)`。

#### 3.2 工具 chunk 幂等沿用现有 ID

- 普通 `tool_use`：`handleRegularToolUse()` 已按 `chunk.id` 查找并合并 input，避免第二个 tool call。
- Task：`SubagentManager.handleTaskToolUse()` 已按 taskToolId 检查 sync/async/pending；消息侧 `ensureTaskToolCall()` 与 `recordSubagentInMessage()` 也按 ID 去重。
- TaskOutput：工具本身不写入可见 `ChatMessage`；只更新 SubagentManager 关联。
- `tool_result`：只更新同 ID tool call，不创建第二个可见块。

需补测试锁定这些不变量，不新增另一套 UI 去重表。

#### 3.3 阶段 1 通知与工具链的边界

`dispatchTaskNotification()` 保持在 transform 之前，位置不挪、行为不改：

- queue-operation XML 与 structured `system/task_notification` 只进入 `SubagentManager.handleTaskNotification()`，命中后早退，不进入 auto buffer。
- 后续模型产生的 TaskOutput tool_use/result 才进入回喂链。
- 通知先销账后，TaskOutput result 找不到 active 条目时返回未处理；因 `TOOL_AGENT_OUTPUT` 为隐藏工具，不生成第二个 UI 块，也不再次销账。
- `handleTaskNotification()` 与 TaskOutput 解析都保持幂等；终态权威性仍只属于通知，回喂链是 UI 投影/兜底，不得反向覆盖通知已写入的终态。

### 4. usage 记账

当前空闲期 usage 已由 `transformSDKMessage()` 正确生成：主 agent assistant message 的 `usage` 合并 input/cache token；result 的 `modelUsage` 只修正 authoritative context window。问题只在最后被 `_autoTurnBuffer` 的旧消费方丢弃。

接入点不新增：auto turn flush 时把 `usage` 原样交给 `StreamController.handleStreamChunk()` 的既有 `case 'usage'`，由其完成：

1. sessionId 防串会话；
2. model 补全；
3. `ChatState.usage` 更新；
4. `onUsageChanged` 刷新 `ContextUsageMeter`；
5. auto callback 末尾 `ConversationController.save(true)` 持久化 usage。

必须在 auto turn 开始前 `resetSpawnedCount()`；否则前一用户轮派过 subagent 时，`subagentsSpawnedThisStream > 0` 会错误吞掉本轮 usage。不得改用 result 聚合 token：其包含 subagent token，违背现有两阶段记账原则。

### 5. turn 完成顺序

auto turn 的 `result` 分支顺序固定为：

```text
复制并清空当前 turn buffer
→ consumeTurnMetadata
→ await auto callback（回喂、finalize、save）
→ 重置 auto text/thinking 去重状态
→ 清 currentTurnSink
→ MessageChannel.onTurnComplete()
```

handler turn 保持现有 generator 语义，但完成时必须使用锁定的 handler，而非完成瞬间数组尾部的 handler。回调异常也执行后四步，避免永久卡住 MessageChannel。

## 风险与权衡

- **共享 StreamController 状态竞争**：若 auto flush 前 MessageChannel 已放行下一用户轮，会污染 `currentContentEl`。因此 auto callback 必须可等待，且 `onTurnComplete()` 后移到回喂完成之后；这是正确性的硬约束。
- **空闲轮中途注册用户 handler**：若不锁定 turn sink，尾部 chunk 会串轮。必须实施 2.1，不能只改 `renderAutoTriggeredTurn()`。
- **空消息闪烁**：临时 assistant DOM 可能短暂建立后被移除。auto 回调在 `result` 后批量执行，通常同一事件循环内完成；仍应以“最终无可见内容则删除”做确定性收口。
- **通知与 TaskOutput 双终态**：保持阶段 1 早退与 SubagentManager 幂等，不增加第二次通知转换；工具链只做投影/兜底。
- **后台保存失败**：UI/内存已正确但 metadata 可能延后持久化。采用 Notice/日志并允许下一次正常保存补齐，不因存储失败回滚终态。
- **非 Claude provider 接口影响**：仅类型签名兼容，Codex/OpenCode 不启用该路径。

### 分步落地与回滚

1. **A：先做 runtime turn sink + async callback，不改 UI 行为。** 用现有 callback 测试确认两类空闲轮只 flush 一次、用户 handler 不串轮。失败时仅回退该组字段与路由改动。
2. **B：新增 InputController auto-turn 消费入口，Tab callback 切换到该入口；删除旧 `renderAutoTriggeredTurn()`。** 测工具链、消息构建与重复渲染。失败时可整体恢复旧 callback，A 可独立保留。
3. **C：接 usage、空消息清理与 save。** 分别验证 meter/state/persistence。若 usage 异常，仅回退 auto turn 前的 spawned-count reset 与 usage/save 接线，不回退工具回喂。
4. **D：更新 provider 文档并跑全套质量门禁。**

不得用 feature flag 长期并存新旧渲染路径；回滚单位是上述提交组，不能让旧 `renderStoredMessage` 与新 StreamController 回喂同时启用。

### 运行时手测

Jest 可证明路由、状态和 DOM 调用次数，但不能证明真实 Claude Agent SDK/Obsidian 时序，以下必须在插件运行态完成：

1. **V5-A 自动唤醒轮**：用户轮派 `run_in_background=true` Task 后停止输入，等待 task-notification 自动唤醒。确认原 subagent 卡片只从 running 变终态一次；自动轮文本、thinking、工具活动按实际顺序显示；无占位消息；usage meter 更新。
2. **V5-B Stop block 续轮**：让主 agent 在后台任务仍运行时尝试结束，触发一次 Stop block；观察续轮内 TaskOutput 工具活动正常显示/更新，最终只出现一套 DOM。
3. **V5-C 并发点击发送**：auto turn 已开始、未到 result 时立刻发用户消息。确认用户消息被排队；auto turn 完整结束并保存后用户轮才开始，双方文本/工具/usage 不串消息。
4. **V5-D 双信号顺序**：分别观察“通知先于 TaskOutput”和“TaskOutput 先于通知”（可通过测试任务时序构造）；同一 subagent 只终态一次。
5. **V5-E 后台 tab**：在非当前 tab 完成任务，确认 tab badge、消息和 usage 更新；切回后无重复重放。
6. **V5-F reload**：auto turn 完成并保存后重载 Obsidian/切换会话，确认消息、工具状态与 usage 和完成前一致。
