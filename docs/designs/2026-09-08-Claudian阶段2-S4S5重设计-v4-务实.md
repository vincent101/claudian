# Claudian 阶段 2 S4/S5 重设计 v4（务实）

## 背景与问题

当前真正未解决的问题不是“Claudian 自己发起的后台轮次如何归属”，而是 **Claudian 完全看不到由其他 SDK 进程持有的独立长跑 session**。`notevault-38` 即此形态：主 transcript 已达约 79 MB、持续追加，既不属于任何 Claudian tab，也不会触发 Claudian runtime、`TurnCoordinator` 或 subagent sidecar 轮询。

因此本版不续做 v3 的两层状态机和全套投影事务，而新增一条与聊天写链隔离的 **只读外部 session 观察链**：发现 session → 按字节增量读取 transcript → 解析活动事件 → 幂等更新观察视图。目标顺序固定为：

1. 看得到外部 session 的工具活动；
2. 在观察视图显示其最新 usage；
3. 不做真流式协议。

代码核查基线为 `/Users/vincentwang/Documents/NoteVault/tools/claudian@3e7bf19c`。背景事实与代码一致，并补充两点：

- Claude 历史读取现为 `fs.readFile` 全文件加载（`sdkSessionPaths.ts:69-98`），不能用于 79 MB 文件的持续轮询；现有解析器可复用事件类型和部分纯解析规则，但 `loadSDKSessionMessages()` 的全量分支过滤、全局 tool-result 收集、排序与合并不适合 tail。
- 仓库已有 `CodexFileTailEngine`，但它同样每 100 ms 全量 `readFileSync` 后按“行号游标”截取；可复用其“cursor + parser state + final drain”概念，不可复用其 I/O 实现。

## 方案设计

### 1. v3 构件逐项裁决

| v3 构件 | 0825-1/当前现状 | 裁决 | 理由 |
|---|---|---|---|
| delivery reservation + attributed lease 两层状态机 | 当前仍是 `ClaudeMessageChannel.activeTurnId` 单锁；0825-1 的 sidecar 链已与主 turn 生命周期解耦 | **丢弃** | 外部 session 根本不经过本插件的 MessageChannel；改锁既不能发现也不能展示它，反而重开高风险核心协议改造 |
| 六道门 + echo 精确绑定 | 当前已有 trailing result、system control、task notification、auto 白名单四类门；仍无 echo 绑定 | **丢弃** | 对外部 transcript 只读无归属竞态；观察事件按 sessionId 和 transcript 顺序归属，不需要 echo |
| `AutoTurnProjectionDraft` 真隔离 | 现有 auto callback 仍是结束后一次性 `renderAutoTriggeredTurn`；外部观察尚无投影路径 | **改造** | 不建通用事务草稿；改为专用 `ObservedSessionState`，它从类型上不持有 `ChatState`、`SubagentManager`、runtime 或 conversation save 入口，天然隔离 |
| Promise ack / 等待投影完成 | 当前 `setAutoTurnCallback` 仍是同步 `void`，runtime 调用后即释放 | **丢弃** | 文件观察没有生产者等待关系；让外部 SDK 等 UI ack 既做不到也无必要 |
| crash replay 适配 | 当前 runtime 仍有自身 query crash replay；外部文件由另一个进程持有 | **改造** | 改成 reader 恢复：保存内存 offset/partial line；文件截断或替换时重置 reader 并按事件键去重，不介入目标进程 replay |
| S-0 八场景 echo 探针矩阵 | 针对 v3 的 UUID/echo 前提 | **丢弃** | 改为 transcript tail 探针：大文件、半行、追加、截断、停止写、进程退出、首条消息 |
| S5 conversation 单写者/ownership | 用户已裁决无同会话多窗口场景 | **丢弃** | 观察页不写 conversation，更不需要 owner/grant/final commit |
| 0825-1 `setTimeout` 自驱轮询 | 已在线验证，具有去重注册、异常退出、终态补读、tab 销毁停止经验 | **保留** | 适合“文件由外部进程追加、本插件只读”的场景 |
| 0825-1 深比较、按 ID 合并、终态收口 | 已用于 sidecar 幂等投影 | **改造** | 外部 transcript 改按 `{uuid, blockIndex, toolUseId}` 归并；只在状态变化时重绘；目标进程退出后 final drain |

结论：v3 的问题定义和主要状态机均已失效。本版不是缩小实施 v3，而是保留已证实的轮询模式，换成外部 session 观察产品。

### 2. 入口形态

#### 推荐：历史菜单中的“外部 Sessions”入口，打开独立只读观察 tab

在现有 history dropdown 增加折叠区“External sessions / 外部 Sessions”：

- 数据来自 `~/.claude/sessions/*.json`，仅展示 `cwd` 规范化后等于当前 vault、transcript 存在的记录；
- 行项目显示 `name`（如 `notevault-38`）、最近写入时间、`运行中 / 安静 / 已离线`；sessionId 仅作次要信息；
- 点击始终在 **新的只读观察 tab** 打开；不把它导入 conversation，不调用 `openConversation()`；
- 观察 tab 顶部明确显示“只读观察”，隐藏输入框、权限按钮、停止按钮和发送快捷键，不创建 `ChatRuntime`；关闭 tab 仅停止观察，不影响目标进程。

推荐理由：入口沿用用户已熟悉的历史菜单，观察内容可长期停留且不阻塞 Obsidian；独立 tab 又能从结构上避开当前 conversation 的 `isStreaming`、`TurnCoordinator` 和保存链。实现时应新增 observer tab 类型/构造分支，而不是给普通聊天 tab 到处追加 `if (readOnly)`。

#### 备选 A：观察 Modal

改动最小、隔离最好，但长期任务中 modal 会遮挡工作区，无法与聊天 tab 并排保留。只适合作为更低成本的第一版；不推荐作为终态。

#### 备选 B：现有会话列表直接导入为 conversation

不推荐。它会诱导 runtime resume、删除、发送、保存等写操作，并把外部 transcript 与 Claudian conversation 双向生命周期混在一起，正好重新引入双进程写竞争。

**待用户拍板项：推荐的新只读 tab，还是更省工的 Modal。** 下文实施步骤按推荐方案写；若选 Modal，仅替换 UI 容器，reader/reducer/lifecycle 不变。

### 4. 数据发现与增量读取

#### 4.1 发现目标 session

首版只支持“从清单手选”，不提供自由路径输入：

1. 扫描 `~/.claude/sessions/*.json`；
2. JSON 结构必须含合法 `sessionId`、`cwd`，可选 `name/pid/startedAt/procStart/entrypoint`；
3. `realpath(cwd)` 必须等于当前 vault `realpath`；
4. transcript 必须由 `getSDKSessionPath(vaultPath, sessionId)` 推导且存在；
5. 以 sessionId 去重，按 transcript mtime 倒序；
6. 排除 Claudian 已登记 conversation 的 provider sessionId，避免同一会话既以聊天 tab 又以 observer tab 出现。需要调试时可提供“显示全部”开关，但不作为首版。

若 registry 已清理但用户持有 sessionId，第二阶段可加“粘贴 sessionId”入口；仍只允许合法 ID 并用固定目录推导路径，禁止任意文件路径。

#### 4.2 首次打开

不能从头读取 79 MB。首次打开采用有界回看：

- 从 EOF 向前分块扫描，默认最多 4 MB；丢弃开头不完整行；
- 最多保留最近 200 条可展示事件或最近一个顶层 user 边界后的事件，以先到者为准；
- 若单条 JSON 超过窗口或没有找到完整边界，界面提示“历史过大，仅显示打开后的新活动”，并从 EOF 开始；不得退化为全文件读取；
- 将首次扫描后的 EOF 记为 byte offset，之后只读追加字节。

4 MB/200 条是保护上限，不是协议语义；实现时集中为常量并以真实 79 MB transcript 做性能验收。

#### 4.3 每轮读取

每次 tick：

1. `stat` 文件；size 未变则不读；
2. size 增大则从 byte offset 读取 `[offset, size)`，与上次 partial buffer 拼接；
3. 仅解析以换行结束的完整 JSON；末尾半行留到下次；
4. 单 tick 最多处理 2 MB，超出则零延迟续排下一小批，避免阻塞 UI；
5. 每个事件生成稳定键：优先 `uuid + contentBlockIndex`，工具事件再用 `toolUseId + phase`；重复键忽略；
6. 文件 size 小于 offset，或 inode/mtime 表明替换：清 reader cursor，保留 UI 已有记录并从新文件有界回看；相同事件键不重复展示；
7. snapshot 深比较后，仅在可见状态变化时通知 renderer。

轮询沿用 0825-1 的自驱 `setTimeout`，不使用 `setInterval`，确保上次读/解析完成后才排下一次。活跃写入时 1 秒；连续 30 秒无变化退到 3 秒；5 分钟无变化退到 10 秒。新数据到达后恢复 1 秒。

### 5. 解析和显示范围

首版只显示对“它在做什么”有直接价值的事件：

| transcript 事件 | 观察行为 |
|---|---|
| 顶层 `assistant.message.content[].tool_use` | 新建/更新工具卡，状态 running |
| `user.message.content[].tool_result` | 按 `tool_use_id` 完成对应工具卡；未见 tool_use 时建占位卡 |
| 顶层 `assistant` text | 显示阶段性说明/最终回复；按 uuid 幂等 |
| 顶层 `assistant` thinking | 默认折叠显示，允许设置中关闭 |
| 顶层 `assistant.message.usage` | 更新观察页 usage，见 §7 |
| `queue-operation`、`attachment`、`last-prompt`、`file-history-snapshot` | 默认不展示，只用于状态判断或忽略 |
| `isSidechain: true` | 首版不混入主时间线；它通常是子 agent 内部细节，避免把 79 MB 噪声全部铺开 |

工具 result 可能极大：内存和 DOM 仅保存前后摘要及“内容已截断”标记，单结果展示上限 32 KB；不复制原始 79 MB 内容。需要全文时只提供“在系统文件管理器定位 transcript”，不在插件内复制或改写。

现有 `parseSDKMessageToChat()` 可复用“assistant text/thinking/tool_use 的字段解释”；但它依赖全局 `toolResults` map、会合并消息且不解析 usage，不能直接作为 tail reducer。实现应提取或调用已有纯 helper，禁止复制一套有分歧的工具结果规范化规则；若为了导出 helper 会触及现有 live/history 路径，必须以现有 history 单测锁住行为。

### 6. 生命周期与状态语义

#### 起链

- 用户在外部 session 清单点击一项；
- observer tab 完成只读容器装配后，先有界回看，再启动 poll chain；
- 同一 observer tab 同一 session 只允许一条链；重复打开时优先激活已有 observer tab，不再起链。

#### 状态

- `running`：目标 PID 可确认存活，且最近有写入；
- `quiet`：进程仍存活但超过 30 秒未写。**quiet 不等于完成**；长命令可能长时间无 transcript；
- `offline`：registry 记录消失或 PID 明确不存在；
- `unknown`：无法可靠确认进程状态，但 transcript 仍可读；不得猜成 completed；
- `error`：连续 5 次读取/解析基础设施失败，停止链并给“重试”按钮。单行 JSON 未完成不算错误，坏行计数后跳过。

#### 停链四出口

对照 0825-1，但适配外部 session：

1. **明确离线**：目标 PID 不存在或 registry 明确移除，执行 final drain 两次（间隔 500 ms）；size 稳定后停止并标 offline；
2. **observer 离开**：关闭 observer tab、切换其观察目标、view/plugin unload，立即清 timer 和文件句柄；普通切到别的 tab **不停链**，以便后台继续更新；
3. **错误上限**：连续 5 次 I/O 错误停止，保留最后快照并允许人工重试；
4. **人工停止观察**：只停 reader，不向目标 session 发 cancel/消息。

不以“长时间没写”自动终止，不设 30 分钟硬上限；这类任务可能数小时运行。为控制资源，后台 observer 降到 3 秒轮询，最多同时观察 3 个 session；超过时要求用户先关闭一个。

插件重载后不自动恢复 observer tab（首版不持久化观察状态），避免重载即扫描旧进程；用户从清单重新打开即可。

### 7. usage 空闲期入账：第二阶段，和“看得到”解耦

首阶段即解析并显示 observer 自己的 usage，但不写任何 Claudian conversation。真实 transcript 已验证可从顶层 assistant 的 `message.usage` 取得 `input_tokens`、`cache_creation_input_tokens`、`cache_read_input_tokens` 和 model；`notevault-38` 当前没有 `result` 行，因此不能依赖 result 的 `modelUsage/contextWindow`。

最小规则：

1. 仅接收 `isSidechain !== true` 的 assistant usage，避免子 agent 累计污染；
2. 同一 assistant uuid 只入账一次，取最新主 agent snapshot；
3. token 合计与现有 `transformClaudeMessage.ts` 一致：三类 input token 相加；
4. context window 优先使用可验证的模型配置；无法识别（例如代理模型名）时显示 token 数，不显示百分比，禁止假填窗口；
5. usage 只写 `ObservedSessionState`，不调用 `StreamController.handleStreamChunk()`，从根上避免与 live runtime 双写。

若后续确有“Claudian 自有 conversation 在主 turn 结束后的 usage 必须持久化”痛点，再单独设计：在既有 auto callback 的唯一写入口内处理 usage，并解决 callback/save 的等待契约。此次不顺手修改，因为当前 callback 同步释放、`renderAutoTriggeredTurn()` 仅渲染 text/tool；直接补异步 save 会与下一用户轮保存竞争，正是 v3 已暴露的结构性风险。

### 8. 真流式协议：本版砍除

外部 transcript 本身只在完整 JSONL 行落盘后可见；本插件既不拥有 SDK 进程，也没有跨进程的开始/逐块/结束通道。把文件轮询包装成“真流式”只是更快回放，不会变成协议流。

若未来出现“逐 token 延迟必须低于文件落盘延迟”的明确需求，应另立轻量 IPC 设计，由目标 SDK 进程主动发布结构化事件，observer 只订阅；不得复活 v3 的 MessageChannel 两层状态机。

### 9. 实施步骤与阶段门

#### P0：真实样本探针，不改产品行为

目标文件：`.context/` 下临时脚本，不提交生产代码。

- 对 `notevault-38` 记录 registry 结构、transcript 顶层类型、assistant/tool/result/usage 形态；
- 验证追加时是否总以换行提交、是否可能出现半行；
- 验证 PID/registry 在 session 退出后的变化；
- 测量 4 MB bootstrap 和每次增量读取耗时、峰值内存；
- 特别记录：该样本无 `result` 行，终态不能依赖 result。

**阶段门**：能仅凭固定 sessionId 安全定位 transcript；工具 use/result 能稳定按 ID 配对；若 PID/registry 无法可靠判终态，状态降级为 unknown + 仅人工停止，不得虚构 completed。

#### P1：字节级 tail reader + 纯 reducer

新增 observation provider 文件及镜像单测：

- byte offset、partial line、2 MB 分批、4 MB 回看；
- append、半行补齐、重复 tick、截断/替换、坏行、连续失败；
- tool_use/result 乱序配对、uuid 去重、超大 result 截断；
- 顶层/sidechain 过滤；usage 去重和未知 context window。

**阶段门**：对 79 MB fixture/脱敏生成文件轮询 100 次，不发生全文件读取，稳定 tick 的新增分配接近零，重复事件不触发 snapshot。

#### P2：session 清单与只读 observer tab

- history dropdown 增加外部 session 区；
- 新增 discriminated observer tab 构造；不实例化 runtime/InputController/TurnCoordinator/ConversationController save 链；
- 接入观察 renderer，复用现有工具卡视觉组件中不带写操作的部分；若现有 renderer 强依赖 ChatState，则只复用叶子组件/样式，不把 observer 塞进 StreamController；
- observer tab 显示 session 名、sessionId、状态、最后更新时间、只读标识、重试/停止观察；
- tab 切换、关闭、plugin unload 生命周期接线。

**阶段门**：代码级断言/测试证明 observer 构造期间 runtime factory 调用次数为 0、save 调用次数为 0、目标 transcript 的 mtime/size 不变。

#### P3：usage 与性能收口

- 接入 observer-local usage；未知模型隐藏百分比；
- 活跃/安静退避、后台 tab 降频、最多 3 链；
- 仅 changed snapshot 重绘，保留工具展开状态；
- 增加状态说明，避免把 quiet 误认为完成。

**阶段门**：长时间无写入不停止、不误报完成；恢复写入后一个活跃轮询周期内更新；工具卡展开状态不因新事件重置。

#### P4：实施复核与发布

流程固定：implementer 落地 → reviewer 独立复核 → 新会话首条消息冒烟 → 干净构建打包。禁止把旧 `main.js`、缓存产物或不同 commit 的构建结果混入包。

干净构建要求：

1. 记录源码 commit 与工作区 diff；
2. 删除/隔离旧构建产物后由同一源码树一次完成依赖检查、测试、build；
3. 核对产物时间、hash、manifest/version 与源码；
4. 仅部署该次产物，保留上一版可回滚备份；
5. 重载 Obsidian 后执行真实冒烟，不以单测代替。

## 风险与权衡

1. **入口待确认**：推荐“历史菜单 → 新只读 observer tab”；Modal 更省工但长期使用差。用户确认前 implementer 不应开工 UI 层。
2. **终态没有可靠 transcript 事件**：真实 `notevault-38` 无 result 行。方案以进程/registry 为辅助信号，无法确认时显示 unknown；宁可不报完成，也不误报。
3. **首次回看有界意味着可能缺旧上下文**：这是避免 79 MB 全量解析和 UI 卡死的明确取舍。用户核心诉求是“现在在干什么”，不是完整导入历史。
4. **工具结果可能极大或敏感**：默认截断、thinking 折叠；观察数据只留内存，不进入 Claudian 持久化 conversation。
5. **现有 history 解析只能部分复用**：类型、字段解释、tool result 规范化有价值；全量分支过滤/排序/合并不适合 tail。强行复用 `loadSDKSessionMessages()` 会把每轮成本退化为 O(文件总大小)。
6. **Codex tail 不能直接复用**：它的 reducer 思路成熟，但 I/O 每轮全量读文件。可以抽象共同接口，但首版不为跨 provider 泛化而重构；Claude observer 先独立落地。
7. **不解决外部 session 控制**：只读红线意味着不能发消息、cancel、approve 或接管 session。这是避免双进程写冲突的安全边界，不是功能遗漏。
8. **不改当前 auto-turn 核心链**：本版不会修 v3 所述极窄归属竞态，也不会让结束后 auto callback 变成实时流。其风险继续维持当前已接受水平，换取改造范围可控。
