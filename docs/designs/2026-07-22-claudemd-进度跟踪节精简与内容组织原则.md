# CLAUDE.md「子 agent 进度跟踪与委托看板」节精简与内容组织原则（理想终态）

## 背景与问题

CLAUDE.md 会话开始即被完整读入系统提示词、每轮对话都占上下文，是稀缺资源。本次会话对进度跟踪机制做了 5 轮排障+设计+落地，每轮都同步编辑「子 agent 进度跟踪与委托看板」这一节（CLAUDE.md 第 90-105 行），使该节从最初几句膨胀到约 16 行，塞进了：协议引用、RUN_ID 下发格式、route_guard.sh 的 NO_RUN_ID 审计逻辑 + 一段 awk 代码块、verify_progress.sh 的 PostToolUse 校验说明、exception_log.tsv 说明、Task* 委托看板阈值规则。

同一批信息已分别写在 `tools/agent_progress/PROTOCOL.md` 和两个脚本的头部注释里。需要判断：这节该收什么、该挪什么，理想终态长什么样，以及一条能防止再次膨胀的长期原则。

本任务走 [理想] 路径：只给目标形态，不计当前改动成本。

## 现状问题诊断

### CLAUDE.md 已有的内容组织惯例（作为判据基线）

CLAUDE.md「常用工具」下三节是同类问题（"背后有一套详细机制"）的既有处理范式：

- **A 股数据查询**（149-159 行）：一句话说清是什么 + 开关方式 + 一行覆盖范围，机制细节在 skill。
- **Web Search 服务**（161-165 行）：一句话说清默认指哪个工具 + 明确"该用哪个/怎么配/怎么降级/怎么运维 → 全部见 skill `websearch-router`，不在此重复维护"。这是全文最干净的指针范式，"不在此重复维护"六个字就是现成的组织原则。
- **KM 文档导入**（132-146 行）：篇幅偏长（含完整命令表），是全文里唯一把可执行命令写进 CLAUDE.md 的例外。可接受的理由是这些命令主会话可能直接手敲、高频、且是"对外接口"而非"内部实现"；但严格说它也偏胖，不宜作为效仿对象。

**判据基线**：CLAUDE.md 该收的是"主会话做决策时要用的路由/触发/阈值信号"（该派谁、何时带 RUN_ID、何时建 Task），不该收的是"协议格式定义、脚本内部审计逻辑、命令示例、日志字段"这类实现细节——后者属于 PROTOCOL.md 和脚本注释的职责。判断关键词：**主会话读这句是为了做决策，还是为了理解实现？** 前者留，后者挪。

## 方案设计（理想终态）

### 一、CLAUDE.md 该节精简为（可直接替换第 90-105 行）

```markdown
### 子 agent 进度跟踪与委托看板

子 agent（implementer/runner/sqlquerier）执行多步骤任务时，用文件写进度替代已失效的 TodoWrite。协议、RUN_ID 格式、脚本审计逻辑全部见 `tools/agent_progress/PROTOCOL.md`，不在此重复维护。

主会话侧只需记住两条行为规则：

- **派 implementer/sqlquerier 时默认带 RUN_ID**：在 prompt 中放独占一行 `RUN_ID: <run_id>`（生成规则见 PROTOCOL.md）。route_guard.sh / verify_progress.sh 会据此做留痕审计，自查协议遵守率的命令见 PROTOCOL.md「审计」节。runner/architect/reviewer 默认单步，不必带。
- **仅多步骤/长任务/有依赖时建 Task**：可选用 `TaskCreate`（metadata 带 run_id）建委托记录、`TaskUpdate` 更新状态；简单/单步/查询类派发不建，避免过度开销。

Agent 定义位于 `.claude/agents/`。
```

从约 16 行降到约 8 行，且移除全部实现细节与代码块。写法对齐「Web Search 服务」节的"一句话 + 全部见 xxx，不在此重复维护"范式。

### 二、挪出内容的去向

绝大部分挪出内容在目标文件中**已存在**，属于"删除 CLAUDE.md 里的复述即可"，而非"搬运"。仅需一处补齐：

1. **RUN_ID 格式/路径推导**（挪出项）→ 已在 PROTOCOL.md 第 14-44 行，**无需搬运，删 CLAUDE.md 复述即可**。
2. **NO_RUN_ID 审计 awk + runner 不标记规则**（挪出项）→ 已在 route_guard.sh 第 13-22 行注释，脚本层已是权威源。但 PROTOCOL.md 目前**缺一个面向主会话的"审计"入口**——建议在 PROTOCOL.md 末尾新增一节，把两个 hook 的审计口径和自查命令收拢为单一权威位置：

   建议在 PROTOCOL.md「主会话读取契约」节之后新增：

   ```markdown
   ## 审计与留痕（hook 侧）

   两个 guard hook 消费本协议的 RUN_ID 标记做事后留痕，实现细节见脚本注释，此处只给主会话自查口径：

   - `tools/guard_hooks/route_guard.sh`（PreToolUse）：把 RUN_ID 写入 routing_log.tsv 第 3 列；implementer/sqlquerier 未带 RUN_ID 则写 `NO_RUN_ID`。自查协议遵守率：

     ```bash
     awk -F'\t' '$2=="implementer" || $2=="sqlquerier"' tools/guard_hooks/routing_log.tsv | \
       awk -F'\t' '{print ($3=="NO_RUN_ID"?"miss":"ok")}' | sort | uniq -c
     ```

   - `tools/guard_hooks/verify_progress.sh`（PostToolUse）：核对 RUN_ID 对应进度文件是否存在且 `status=done`，异常静默记入 `tools/guard_hooks/exception_log.tsv`（时间戳\trun_id\t异常类型），不打断流程。
   ```

   这样 CLAUDE.md 指向 PROTOCOL.md「审计」节，PROTOCOL.md 给自查命令 + 指向脚本注释看实现，形成单向指针链，awk 命令只在 PROTOCOL.md 和脚本注释各存一份（脚本注释是自解释必需，PROTOCOL.md 是主会话入口，二者受众不同，可接受；关键是从 CLAUDE.md 消除第三份）。

3. **verify_progress.sh 校验行为 + exception_log 字段**（挪出项）→ verify_progress.sh 注释已权威，PROTOCOL.md 上面新增节点一句带过即可，**删 CLAUDE.md 复述**。
4. **Task* 字段清单（subject/owner/metadata）**（挪出项）→ 若要留说明，进 PROTOCOL.md 或新建极短的委托看板说明；但更简单的处理是直接省略字段清单（TaskCreate 参数自解释），CLAUDE.md 只留"何时建/不建"的阈值。

**不建议新建独立文档**：现有 PROTOCOL.md 完全能承载，新建文档反而增加一个需要维护和索引的对象，违背精简初衷。

## 风险与权衡

- **信息可达性**：精简后主会话不再能"一眼在 CLAUDE.md 里读到全部审计命令"，需多跳一层去 PROTOCOL.md。权衡：CLAUDE.md 每轮必读、寸土寸金，审计命令是低频动作（自查遵守率不是每轮都做），下沉收益（省上下文 + 消双写）大于多跳一层的成本。这与 websearch-router 节的取舍一致。
- **KM 节的既有偏胖**：本方案不动 KM 节，但它是全文里下一个候选精简对象；若日后统一收口，KM 命令表也可下沉到 SKILL.md，CLAUDE.md 只留一句指针。此处仅提示，不纳入本次范围。
- **迁移/落地代价**（理想路径知情项）：改动极小——CLAUDE.md 删 12 行、留 8 行；PROTOCOL.md 加约 15 行。无代码改动、无行为变更（脚本本就按注释运行，CLAUDE.md 只是文档）。代价近乎为零，理想终态与务实落地在此高度重合。

## 长期组织原则（建议写入 CLAUDE.md）

建议在 CLAUDE.md「项目概述 > 工作规范」或「任务分工」开头加一条元原则，指导以后"新机制该写进 CLAUDE.md 多少"：

> **CLAUDE.md 只收"主会话做决策要用的信号"（该派谁/何时触发/阈值/红线），不收"协议格式、脚本实现、命令示例、日志字段"这类实现细节——后者写进对应 skill/协议文档/脚本注释，CLAUDE.md 只留一句指针 +「不在此重复维护」。判断法：读这句是为决策还是为理解实现？为理解实现的，一律下沉。同一事实严禁在 CLAUDE.md 与其权威源双写。**

配套自查习惯：任何机制迭代后，先改权威源（脚本/协议文档），CLAUDE.md 只在"决策信号本身变了"时才动；若发现改脚本要连带改 CLAUDE.md 里的复述，说明该处复述就是应删的双写。
