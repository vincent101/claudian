# Claudian 标题栏"等待用户回答"状态颜色方案

## 背景与问题

用户希望在 Claudian 的 tab 状态颜色（灰=未运行 / 红=运行中 / 蓝=当前窗口）之上，新增一种颜色表示"Claude 正在等待我回答问题"。

**调研结论：这个功能不需要设计，上游已经做完了。** 本地装的是 2.0.11，上游 2026-08-05 发布的 2.1.0 已实现完整的 attention 状态机并接入了三类交互（工具授权 / AskUserQuestion / Plan 决策）。本文档的实质内容因此从"如何新增状态"转为"如何拿到这个已有能力"。

### 事实核查（全部有据）

**1. 三种颜色的真实定义位置**

用户说的"标题栏"实际是插件自绘的 **tab badge**（数字小方块），不是 Obsidian 的 tab header。已确认插件**完全没有**操作 Obsidian 的 leaf/tabHeaderEl：

```
# 上游 2.1.2 源码全仓搜索，零命中
grep -rn "tabHeaderEl|tabHeaderInnerTitleEl|view-header|workspace-tab-header" src/
# 本地 bundle 同样零命中
grep -c "tabHeaderEl" .obsidian/plugins/claudian/main.js  → 0
```

颜色定义在 `/Users/vincentwang/Documents/NoteVault/.obsidian/plugins/claudian/styles.css`：

| 行号 | 类名 | 颜色来源 | 用户认知 |
|---|---|---|---|
| 238 | `.claudian-tab-badge-active` | `var(--interactive-accent)` | 蓝色 = 当前窗口 |
| 243 | `.claudian-tab-badge-streaming` | `var(--claudian-brand, #da7756)` | 红色 = 运行中 |
| 259 | `.claudian-tab-badge-attention` | `var(--text-error)` | **已存在但从不触发** |
| 263 | `.claudian-tab-badge-idle` | `var(--background-modifier-border)` | 灰色 = 未运行 |

切换逻辑在 `main.js:90225-90232`（未压缩，可直接 grep `claudian-tab-badge-idle`），优先级 `active > attention > streaming > idle`。

无 Style Settings 集成（`grep "@settings" src/style/` 零命中）；`--claudian-*` 变量层存在于 `styles.css:9-20`，但仅用于 provider 品牌色，不含状态色。

**2. "等待用户回答"状态的可挂钩信号 —— 关键差异**

**本地 2.0.11：状态槽位存在，但是死代码。** `needsAttention` 有 getter/setter（`main.js:85449-85457`）、有回调链路（`onAttentionChanged` → `onTabAttentionChanged` → `updateTabBar`，`main.js:90363`/`91139`）、有 CSS 类，但**全仓没有任何一处把它设为 true**：

```
grep -n "needsAttention" main.js
# 唯一赋值是 setter 内部的 this.state.needsAttention = value（85454）
# 没有任何调用方
```

上游 2.0.11 源码同样如此，只有单测在设 true（`tests/unit/.../ChatState.test.ts:346`）。所以在 2.0.11 上，这是一条**已铺好但没接电的线**。

**上游 2.1.0+：完整实现，且语义比用户要求的更细。** `src/features/chat/state/types.ts:45` 定义：

```ts
export type TabAttentionKind = 'review' | 'action-required';
export type TabAttention = { kind: TabAttentionKind; since: number } | null;
```

- `action-required` = 正在阻塞等用户操作（正是用户想要的语义）
- `review` = 后台 tab 已跑完、有新内容待查看

三类交互全部接入 `src/features/chat/tabs/Tab.ts:755/780/794`，用 try/finally 保证配对释放：

| 交互 | 触发点 |
|---|---|
| 工具授权（Permission required） | `Tab.ts:755` `requestApproval` |
| AskUserQuestion | `Tab.ts:780` `askUserQuestion` |
| Plan 决策（ExitPlanMode） | `Tab.ts:794` `requestPlanDecision` |
| Plan 审批（另一路径） | `InputController.ts:650` |

状态机在 `src/features/chat/state/ChatState.ts:319-361`，用 `pendingActionIds: Set<string>` 做引用计数（多个并发请求不会互相踩），`endActionRequired` 清空后降级回 `review` 或 `null`；切到该 tab 时 `acknowledgeReview()` 自动消除 review（`TabManager.ts:316`）。

**这是可行性的核心结论：2.0.11 上无信号可挂钩，2.1.0+ 上信号完备且质量高于自研。**

**3. main.js 可 patch 性**

- **本地 main.js 未压缩**：93219 行，平均 38 字符/行，无 `sourceMappingURL`。变量名完整保留，可读可 patch。
- **但上游 release 产物是压缩的**：`esbuild.config.mjs:196` `minify: prod`。下载 2.1.2 的 main.js 为 960 行、平均 3545 字符/行，局部变量已被 mangle（`renderBadge(n)` / `renderBadge(e)`）。
- 那么本地这份未压缩的 3679919 字节是哪来的？已验明：**本地 `main.js.bak-before-xhigh-patch` 与 2.0.11 官方 release asset 字节完全一致**（`cmp` 通过，同为 3679854 字节）。即 2.0.11 那一版官方发布的就是未压缩产物，上游后来才启用了压缩。这意味着**升级后 patch 难度会显著上升**。
- 无完整性校验（Obsidian 不校验插件文件哈希）。
- **自动更新会覆盖 patch**：`claudian` 在 `.obsidian/community-plugins.json` 里，走社区插件更新，更新即整体覆盖 main.js/styles.css。Obsidian 无官方"锁版本"开关，只能靠不点更新。

**4. 上游正规路径可用性（已实测）**

- 仓库：`YishenTu/claudian`（14570 star，MIT，`pushed_at: 2026-08-06`，非常活跃）
- 版本节奏极快：2.0.44(08-03) → 2.1.0/2.1.1/2.1.2 全在 08-05 当天
- **依赖可安装**：`bun install --ignore-scripts` 成功，666 包 / 55 秒
- **构建可复现**：`npm run build` 成功；产出的 `styles.css` 与 release asset **字节完全一致**；`main.js` 3404964 vs release 3404442（522 字节差，属依赖补丁版本漂移，非实质差异）
- 本机工具链满足要求：`node v25.6.1`（package.json 要求 `>=24 <25`——实际是 25.6.1，**超出上界**但构建实测通过）、`bun 1.3.9`
- 无相关 issue/PR 需要提：功能已合并进 2.1.0

**5. 附带发现：本地那个 xhigh patch 已被上游吸收**

本地 main.js 相对 .bak 只多一行（`main.js:55733`）：

```js
if (isBuiltInFamilyVariant(normalized, "sonnet")) return true;
```

作用是让 `sonnet`/`sonnet[1m]` 支持 xhigh effort。上游 2.1.2 已重构为配置表驱动，`src/providers/claude/modelTiers.ts:34` sonnet 的 `aliasSupportsXHigh: true` —— **语义等价，升级后无需重新打这个补丁**。这消除了升级的主要顾虑。

## 方案设计

### 方案 A（推荐）：升级到上游 2.1.2，零代码改动

功能白拿，不写一行代码。

**步骤**

1. 备份现状：把 `/Users/vincentwang/Documents/NoteVault/.obsidian/plugins/claudian/` 整目录复制一份（含 `data.json`）
2. 在 Obsidian 内 Settings → Community plugins → 检查更新 → 更新 Claudian 到 2.1.2
3. 重启 Obsidian（或 disable/enable 插件）
4. 删除已无用的 `main.js.bak-before-xhigh-patch` 和 xhigh patch 记录（上游已吸收，见事实 5）
5. 验证（见"验证方式"）

**改动点清单**：无源码改动。仅插件目录被官方产物覆盖。

**维护成本**：最低。后续升级正常走官方更新，不需要重打任何补丁。

**失效风险**

- 跨了 2.0.11 → 2.1.2 共 15 个版本，**2.1.0 引入 dual-pane 会话管理**（release note: `feat: add dual-pane session management #1050`），UI 布局有实质变化。
- **`tabBarPosition` 设置在 2.1.x 已被移除**（上游全仓 grep 零命中；2.0.11 本地 bundle 有 `main.js:26607`），tab bar 改为固定位置 + `tabCount >= 2` 时自动显示（`ClaudianView.ts:621-628`）。如果用户依赖 `tabBarPosition: "input"` 的布局，观感会变。
- 本地 `data.json` 只存了 `tabManagerState`（8 个 tab + activeTabId），没有自定义设置项，迁移风险很低。上游有 legacy 字段迁移逻辑（`ClaudianSettingsStorage.ts:77-84` 等）。
- 回滚成本低：把备份目录拷回即可。

**可行性判定：可行**。依据：功能已在上游实现并接入三类交互；构建/依赖实测通过；本地唯一 patch 已被上游吸收；有干净回滚路径。

### 方案 B（用户已选定，以下为可执行方案）：留在 2.0.11，手工 patch bundle 接通 needsAttention

**用户决策**：留在 2.0.11（已知悉升级即失效）；颜色用橙色；优先级保持 `active > attention` 不动；review 与 action-required 同色（2.0.11 的 `needsAttention` 是 boolean、无 kind 区分，天然满足）。

**可行性判定：可行**。依据：bundle 未压缩、函数名完整；`needsAttention` setter 已自带 `onAttentionChanged` 回调触发 `updateTabBar()`（`main.js:85452-85457` → `90363` → `91139`），即**只要赋值就会自动重绘，无需碰渲染逻辑**；CSS 类已存在。

#### B.0 先纠正上一版的一处错误

上一版写"推荐改 `main.js:90094/90106/90112` 三处调用方"，措辞会引起误解——那不是渲染侧，而正是**触发侧**：这三行位于 `function setupServiceCallbacks(tab, plugin)`（`main.js:90089`），是本地 bundle 中**与上游 `tabs/Tab.ts:755/780/794` 精确对应的位置**。选它作为 patch 点的理由（已核实）：

- 它是 per-tab 的（调用方 `main.js:89875` / `90842` 均传入具体 `tab`），闭包内 `tab` 直接可见，`tab.state` 就是该 tab 的 ChatState 实例
- 三个 callback 紧邻（90091-90126），改动集中在 36 行内
- 是 provider → UI 的唯一入口：provider 侧统一经 `approvalCallback` / `askUserQuestionCallback` / `exitPlanModeCallback` 调进来（`main.js:60743-60770`、`68805/68829/68849`、`74411`），在此处包一层即可覆盖所有 provider（Claude / Codex / OpenCode）

#### B.1 触发侧完整清单：等待开始 / 结束的确切位置

**注意：共有 4 条路径，不是 3 条。** 上一版和派单都漏了第 4 条（Plan 完成后的审批），它不经 `setupServiceCallbacks`。

| # | 交互 | 开始等待 | 结束等待 | 形态 |
|---|---|---|---|---|
| 1 | 工具授权 / permission | `main.js:90092` callback 入口 | `await` 返回 | `async` 箭头函数，`await handleApprovalRequest(...)` |
| 2 | AskUserQuestion | `main.js:90104` callback 入口 | `await` 返回 | `async` 箭头函数，`await handleAskUserQuestion(...)` |
| 3 | Plan 决策 / ExitPlanMode | `main.js:90110` callback 入口 | `await` 返回（注意后面还有 `decision` 后处理，需包住整段） | `async` 箭头函数 |
| 4 | **Plan 完成后审批（漏项）** | `main.js:80245` `await this.showPlanApproval()` 之前 | 该 `await` 返回之后 | 在 `InputController` 内，用 `this.deps.state` |

Promise resolve 的落点（决定 `finally` 是否可靠）：

- 路径 1/2/3 最终都走 `showInlineQuestion`（`main.js:80909`）→ `new Promise` → `InlineAskUserQuestion` 的 `resolveCallback`（`main.js:80918` 正常完成 / `80929` render 异常 reject）
- 路径 4 走 `showPlanApproval`（`main.js:80988`）→ `new Promise` → `InlinePlanApproval` 回调（`81003` 正常 / `81013` reject）

**取消/异常路径已验证安全**：`InlineAskUserQuestion.destroy()`（`main.js:78106-78108`）内部调用 `handleResolve(null)`，而 `handleResolve`（`main.js:78590-78602`）有 `if (!this.resolved)` 幂等守卫并调用 `resolveCallback(result)`。即 **`dismissPendingApproval()`（`main.js:80975`，被 `89783`/`90052` 调用）强制关闭时，Promise 会以 `null` resolve，而不是悬挂**。abort signal 路径同理（`main.js:78102` `abortHandler = () => this.handleResolve(null)`）。

结论：**用 `try/finally` 包住 `await` 即可覆盖全部正常/取消/异常路径，不会卡在橙色。** 这是本方案能成立的关键前提。

#### B.2 并发问题：必须复刻计数器，boolean 不够

**结论：必须做引用计数。不能用裸 boolean。**

代码依据（三条，指向同一结论）：

1. **作者自己就用了深度计数器。** 同一份代码里管理输入框显隐的 `inputContainerHideDepth`（声明 `main.js:79962`，`hideInputContainer` 自增 `81029`，`restoreInputContainer` 自减并仅在归零时恢复 `81033-81036`）——如果同一 tab 永远只有一个 pending 交互，这个 depth 计数器毫无意义。作者用它，说明**嵌套/并发的等待是预期内的**。
2. **pending inline 是三个独立字段，不是一个。** `pendingApprovalInline` / `pendingAskInline` / `pendingExitPlanModeInline`（`main.js:79956-79958`）+ `pendingPlanApproval`（`79959`）各自独立，可同时非空。
3. **provider 侧有并发来源。** subagent 可并行（`SubagentManager` 用 `activeAsyncSubagents` / `pendingAsyncSubagents` 两个 Map，`main.js:84436-84437`；`hasRunningSubagents()` 判 `size > 0`，`84714`），且授权请求携带 `agentID`（`main.js:60764`、UI 展示于 `80841`），说明子 agent 会各自发起授权。裸 boolean 在"A、B 两个请求，A 先完成"时会提前清除，B 仍在等却已恢复灰色。

**最小实现**：不引入 Set（不需要 id 去重，`try/finally` 已保证严格配对），用**整数计数器挂在 `tab.state.state` 上**，避开与 setter 的递归。具体见 B.3 的 Patch 3。

**Patch 3 — 新增引用计数方法**

文件：`main.js`，行 85452-85457（`ChatState` 的 `needsAttention` setter）。锚点 `    this.state.needsAttention = value;`（命中 1 次）。

在 setter 之后追加两个方法。old（完整 setter）：
```js
  set needsAttention(value) {
    var _a3, _b2;
    this.state.needsAttention = value;
    (_b2 = (_a3 = this._callbacks).onAttentionChanged) == null ? void 0 : _b2.call(_a3, value);
  }
```
new:
```js
  set needsAttention(value) {
    var _a3, _b2;
    if (this.state.needsAttention === value) return;
    this.state.needsAttention = value;
    (_b2 = (_a3 = this._callbacks).onAttentionChanged) == null ? void 0 : _b2.call(_a3, value);
  }
  beginAttention() {
    this.state.pendingAttentionCount = (this.state.pendingAttentionCount || 0) + 1;
    if (this.state.pendingAttentionCount > 0) this.needsAttention = true;
  }
  endAttention() {
    if (!this.state.pendingAttentionCount) {
      this.needsAttention = false;
      return;
    }
    this.state.pendingAttentionCount -= 1;
    if (this.state.pendingAttentionCount <= 0) {
      this.state.pendingAttentionCount = 0;
      this.needsAttention = false;
    }
  }
```

说明：
- setter 加了 `if (=== value) return` 幂等守卫（对齐上游 `setAttention` 的去重语义，`ChatState.ts:497-506`），避免每次 begin/end 都触发一次全量 `updateTabBar()` 重绘
- `beginAttention` / `endAttention` 通过 `this.needsAttention =` 走 setter，从而复用既有回调链，**不需要碰 TabBar 渲染代码**
- 计数字段存在 `this.state` 上，随 `createInitialState()` 初始化
